# «Мои мероприятия» — итерация 2

**Тип:** implementation specification для Claude Code  
**Основа:** представленные пользователем макеты desktop и mobile, 23.09.2026  
**Связанный документ:** брендбук Soft Editorial Glass (визуальные токены и компоненты).  
**Цель экрана:** за минуту показать организатору, в каком проекте требуется действие, и дать прямой переход к предмету работы.

## 1. Объём этой итерации

Доработать существующую страницу, сохранив верхнюю панель, заголовок, создание свадьбы, блок «Требует внимания», вкладки «Активные / Архив», поиск, сортировку и список проектов. Не переписывать продуктовую архитектуру и не добавлять фиктивные сущности ради макета. Применять фирменные токены из брендбука; при расхождении цветовых чисел этот документ определяет поведение, брендбук — оформление.

**Приоритет:** (P0) корректность данных, статусов, ссылок и мобильного доступа к проектам; (P1) плотность и визуальная иерархия; (P2) фото или фирменный акцент, если у проекта уже есть такие данные.

## 2. Данные и вычисления

### 2.1 Проект

Использовать существующую модель проекта, сопоставив поля: `id`, `title` (например, «Мария + Илья»), `eventType`, `eventDate` (может отсутствовать), `venue` (может отсутствовать), `lifecycleStatus`, `coverImage` (опционально), `teamMembers` и связанные задачи. Не вычислять статус проекта из даты события. После даты свадьбы проект может оставаться открытым для финальных расчётов и закрывающих задач.

Для отображения нужны понятные стадии:
- `active`, дата в будущем: «В подготовке»;
- `active`, дата прошла: «Завершение проекта» (лишь отображаемая метка; не менять сохранённый статус автоматически);
- `active`, дата не указана: «В подготовке», справа «Дата уточняется»;
- `archived`: «В архиве».

Если действующая модель имеет другие значения, сделать явное отображение, не вводить тихую миграцию данных.

### 2.2 Задача и сигнал внимания

Задача имеет `id`, `projectId`, `title`, `status`, `dueAt` (опционально), `assignee` (опционально), `blockedReason` (опционально). Завершённые и отменённые задачи исключаются из внимания. Одной задаче соответствует не более **одной** строки внимания. Приоритет её причины: `blocked` → `overdue` → `dueToday`; если блокировка и просрочка совпали, можно показать оба признака в деталях задачи, но здесь строка одна. Заблокированность должна быть явным состоянием/признаком, её нельзя выводить из просрочки.

Расчёт времени выполняется в часовой зоне агентства; если настройки зоны ещё нет — в зоне пользователя с явно централизованным хелпером. Сравнивать с текущим временем: `dueAt < now` — «Просрочено»; срок сегодня и ещё не наступил — «Сегодня · HH:mm»; просрочка ровно на календарный день — «Просрочено 1 день», несколько дней — «Просрочено N дней»; если просрочено менее суток, лучше «Просрочено с HH:mm», чем «1 день». Если `dueAt` хранит только дату, срок истекает в конце этого календарного дня, показывать «Сегодня» без выдуманного времени. Ни дедлайн завтра, ни сегодняшний будущий дедлайн не являются просроченными.

Порядок сигналов: заблокированные и просроченные выше задач со сроком сегодня; внутри каждой группы — старший срок выше; при совпадении — стабильная сортировка по `projectId` и `taskId`. Если продукт уже задаёт важность блокировки относительно просрочки, сохранить её и задокументировать. Счётчик «Требует внимания · N» показывает **все** уникальные релевантные задачи во всех доступных активных проектах, а не только видимые пять и не число проектов. Архивные проекты исключить. «Срочно · N» в карточке — число таких задач только в этом проекте.

В строке сигнала показывать краткий статус, название задачи, название проекта и ответственного, если указан. При отсутствии ответственного — «Не назначен». При отсутствии даты у заблокированной задачи не показывать срок. Длинные названия должны переноситься или обрезаться с доступным полным текстом, без исчезновения кнопки перехода.

### 2.3 «В работе»

Не называть задачу «процессом» автоматически. Блок «В работе» показывает до двух незавершённых задач со статусом `in_progress` в этом проекте. Если их нет — «Пока нет задач в работе». Если несколько, сортировать по ближайшему сроку, затем по последнему обновлению; не показывать завершённое или архивное. При отсутствии надёжного статуса `in_progress` лучше временно скрыть строку, чем подменять её случайной задачей.

## 3. Поведение блоков

### 3.1 Шапка

Заголовок «Мои мероприятия» и действие «+ Создать свадьбу» остаются. Тестовые подписи «Тестовое агентство», «Тестовый стенд» показывать только в тестовой среде. На узком экране название агентства не обрезать так, чтобы возникала неразличимая надпись «Тестовое агент…»: использовать короткое имя или убирать его из шапки под доступное меню профиля. «Выйти» должен быть доступен через меню без горизонтального переполнения. Если позже поддерживаются не только свадьбы, текст кнопки будет определяться типом создаваемого мероприятия; в этой итерации не переименовывать его без изменения сценария создания.

### 3.2 «Требует внимания»

Верхний блок остаётся самым заметным, но не должен занимать весь первый экран телефона. На desktop по умолчанию до **5** строк, на mobile до **3**. Кнопка «Показать все N» раскрывает весь список в этом же блоке; «Свернуть» возвращает исходный лимит. N — количество скрытых строк. Если сигналов 0, показать спокойное состояние «Сейчас ничего не требует срочного решения» и заметную ссылку к проектам; не оставлять большую пустую тёмную панель. Если сигналов много, раскрытый список должен быть управляемым: при большом объёме (например, более 20) использовать отдельный список с постраничной или постепенной подгрузкой, не рендерить сотни строк без ограничения.

Клик по строке и её стрелке открывает **конкретную задачу в соответствующем проекте**, например маршрут проекта с `taskId`/панелью задачи. Прямой URL должен работать после обновления страницы и при открытии в новой вкладке. Если задача удалена или доступ отозван, показать понятное сообщение и безопасный переход к проекту/списку. Строка целиком интерактивна, с фокусом клавиатуры; вложенных конкурирующих ссылок в ней нет.

### 3.3 Управление списком проектов

«Активные (N)» и «Архив (N)» считают проекты, доступные текущему пользователю, отдельно. Поиск ищет по названию пары/проекта и площадке, без учёта регистра, с понятным пустым состоянием; не смешивать результаты активной вкладки и архива. При очистке поиска вернуться к обычному списку. Поиск и сортировка не должны менять глобальный блок внимания.

Сортировка «По дате»: будущие проекты по возрастанию даты, затем активные проекты с прошедшей датой, затем без даты; внутри групп — стабильный вторичный ключ по названию и `id`. Это не скрывает проекты после события, но не заставляет прошлую свадьбу постоянно стоять первой. Если продукт требует другого порядка, явно обозначить этот вариант в селекте. Дополнительные варианты сортировки добавлять только если они реализованы, не создавать неработающие элементы интерфейса. В архиве сортировка по дате события по убыванию разумнее; выбрать и явно подписать вариант в интерфейсе.

### 3.4 Карточка проекта

Сохранить дату как крупный визуальный ориентир, название пары, тип/площадку, срочные пункты и «В работе». Сделать карточки компактнее: не задавать большую фиксированную высоту и не выравнивать кнопку по нижнему краю ценой большого пустого пространства. Карточки в одной строке могут иметь одинаковую высоту за счёт CSS grid, но содержимое должно задавать минимальную высоту; при длинных данных карточка растёт. Блок «Срочно · N» содержит **первый релевантный сигнал** и фразу «и ещё N−1» при необходимости; статус/текст согласованы с верхним списком. Красную обводку применять только при настоящем сигнале внимания; без сигнала — нейтральная рамка. Не показывать одновременно «Срочно» и «Нет задач в работе» как противоречие: это разные состояния, но различие должно быть ясно из подписей.

В карточке прошедшего мероприятия показать «Завершение проекта», дату прошедшего события и относящиеся к закрытию задачи. Для проекта без даты показать «Дата уточняется» вместо пустого числа. Название, площадка и действия выдерживают длинные строки и кириллицу. «Открыть проект» ведёт в обзор проекта; можно сделать кликабельной всю карточку при условии, что внутри нет несовместимых отдельных действий и фокус виден.

## 4. Адаптив и визуальная иерархия

Desktop: ограниченная ширина контента по брендбуку; две карточки проекта в ряд при достаточной ширине, одна при сужении. Сетка не должна создавать третью колонку без проверки читаемости. Блок внимания заметен, но его высоту определяют строки, а не крупный постоянный `min-height`.

Mobile: порядок — заголовок → кнопка создания → блок внимания с тремя строками → вкладки/поиск/сортировка → карточки в одну колонку. Поиск и сортировка доступны без горизонтального скролла, могут стоять друг под другом. В мобильной строке внимания порядок: статус → задача → проект/ответственный; стрелка не перекрывает текст. Размер интерактивных целей не менее 44×44 CSS px. Избегать тяжёлого тёмного блока на несколько экранов высотой. При раскрытии всех сигналов пользователь может свернуть список и добраться до проектов.

Визуальный язык: использовать брендбук как источник цветов, шрифтов, радиусов, отступов и состояний. На этой странице достаточно одного выразительного тёмного блока. Карточки должны оставаться рабочими и читаемыми. Если `coverImage` уже доступен, можно использовать его дозированно внутри карточки с обеспеченным контрастом; **не добавлять случайные стоковые фотографии и не делать загрузку фото обязательной**. Если фото нет, использовать предусмотренный брендбуком нейтральный/акцентный фон. Не переносить glass-эффект на строки длинного списка внимания или плотные данные.

## 5. Состояния, надёжность, доступность

- Загрузка: скелетоны по форме блоков, без показа нулевых счётчиков как фактических данных.
- Ошибка загрузки: сообщение и «Повторить», без ложного «Нет мероприятий».
- Нет проектов: краткий onboarding с кнопкой создания; не показывать пустой огромный блок внимания.
- Проекты есть, сигналов нет: компактное спокойное состояние.
- Поиск ничего не нашёл: отдельный текст с действием «Очистить поиск».
- Ограниченные права: только доступные пользователю проекты/задачи; не раскрывать чужие данные через глобальный счётчик или прямой URL.
- Обновления: после изменения задачи, срока, статуса, архивации или создания проекта блок внимания и карточки должны пересчитываться из одного источника данных, без ручной правки счётчиков. Состояние на нескольких вкладках согласуется после повторного открытия/обновления; если есть live updates — использовать их.
- Время: обновлять метки «Сегодня/Просрочено» при возвращении на вкладку и переходе через границу дня, не ждать перезагрузки на следующий день.
- Доступность: семантические заголовки, кнопки/ссылки, видимый фокус, контраст по брендбуку, статусы выражены текстом, не одним цветом; действия с клавиатуры.

## 6. Критерии приёмки

1. На мобильном экране после первых трёх сигналов есть действие раскрытия; список проектов достижим без прокрутки через все семь строк.
2. «Требует внимания · 7» при пяти/трёх видимых строках остаётся 7; «Показать все 7» раскрывает полный набор без дубликатов.
3. Сегодняшняя задача со сроком 19:20 в 17:00 обозначена «Сегодня · 19:20»; после 19:20 — просрочена. Завтрашняя задача не просрочена.
4. Заблокированная и одновременно просроченная задача занимает одну строку и считается один раз.
5. Клик по сигналу открывает нужную задачу нужного проекта; ссылка работает после обновления страницы. «Открыть проект» открывает обзор проекта.
6. Событие, дата которого прошла, остаётся в активной вкладке до явной архивации и имеет метку «Завершение проекта»; при сортировке будущие даты идут прежде прошедших.
7. Отсутствующая дата отображается «Дата уточняется»; название/площадка в две и более строки не ломают карточку.
8. Архивные и недоступные проекты исключены из глобального блока внимания и его числа.
9. После завершения задачи число внимания и срочный блок нужной карточки обновляются согласованно.
10. В состояниях загрузки/ошибки/пустого списка экран не выдаёт вымышленных задач и чисел.

## 7. Что передать вместе с этим ТЗ

Брендбук Soft Editorial Glass; текущие desktop/mobile макеты; существующие типы данных, маршруты, API и компоненты проекта. Claude Code должен встраивать изменения в текущую реализацию, не создавать вторую параллельную модель задач или проектов. Если реальная схема не содержит `blocked` или `in_progress`, сначала указать отсутствующее поле и предложить минимальное изменение схемы/контракта; не симулировать нужный статус по названию задачи.

## 8. Нерешённое продуктовое правило (не блокирует правки компоновки)

Нужно закрепить, кому показывается общий блок внимания: **все доступные задачи агентства** или **только задачи, за которые отвечает текущий пользователь**. Для текущего прототипа принять «все доступные активные проекты агентства», поскольку экран показывает состояние проектов команды. При появлении ролей и распределения нагрузки добавить фильтр «Мои / Команды», сохранив понятную подпись для выбранного режима.
