# Обзор мероприятия — спецификация v1 для Claude Code

**Экран:** конкретный проект после перехода из «Мои мероприятия».  
**Основа:** текущий прототип проекта «Мария + Илья» на присланном мобильном макете; единое ТЗ экрана «Мои мероприятия»; брендбук Soft Editorial Glass.  
**Цель:** организатор открывает свадьбу и быстро отвечает на три вопроса: **что требует решения сейчас, что реально выполняется и где мы ждём ответа или действия другого человека**. Затем он переходит прямо к нужной задаче.

## 0. Границы и договорённости

Это рабочий обзор существующего проекта, а не полный модуль задач, календарь, финансы или карточка подрядчика. Показывать только данные, которые уже есть в модели/контракте. Не создавать видимость интеграции с перепиской, автоматических напоминаний клиентам, платежей и согласований, если они ещё не реализованы. Все пункты обзора должны иметь источник: существующую задачу или явно созданное состояние проекта.

Использовать общие компоненты и расчёт срочности с экраном «Мои мероприятия», чтобы одно событие имело одинаковый статус и число в обоих местах. Применить визуальные правки последней дизайн-итерации: небольшие статусные бейджи, тонкие границы, без двойных контуров и без тяжёлой чёрной панели. На проектном обзоре может быть собственный голубой акцент, но не дублировать большой блок глобального списка дословно.

**Принятое MVP-допущение:** обзор доступен участникам агентства, имеющим доступ к проекту; по умолчанию показывает доступную работу всей команды проекта. Персональный режим «Мои задачи» вводить позднее, если появится чёткая модель назначения и ролей. Не отфильтровывать молча задачи других участников.

## 1. Структура экрана

### 1.1 Навигация и шапка проекта

- Ссылка «← Мои мероприятия» возвращает к списку. При открытии проекта из поиска/архива желательно сохранять предыдущую вкладку и параметры списка в URL или навигационном состоянии; прямой вход ведёт к стандартному списку.
- Тип мероприятия над названием: «Свадьба».
- Крупное название проекта («Мария + Илья»), доступное название для screen reader; длинные названия переносятся, без обрезки главной идентификации проекта.
- Дата полным читаемым форматом и площадка, если указана. Если даты нет: «Дата уточняется»; если площадки нет, скрыть её, не показывать тире или «undefined».
- Статус проекта: «В подготовке» при активном будущем событии, «Завершение проекта» при активном проекте после даты события, «В архиве» для архивного. Прошедшая дата не архивирует проект сама.
- При будущем событии можно показать «через N дней» только если расчёт использует часовой пояс агентства и дату мероприятия; в день события — «Сегодня». Отрицательное «через −N дней» запрещено.
- Меню действий проекта (иконка + понятное имя/подсказка): редактировать базовые данные; перенести в архив при разрешённой роли. «Переместить в архив» не выводить отдельной первичной кнопкой под названием. В архивном проекте показывать действие восстановления, если оно поддерживается.
- Если фото обложки реально сохранено, отображать в компактной шапке в соответствии с брендбуком; отсутствие фото не должно оставлять пустое место или подменяться случайным стоком.

### 1.2 Краткая ориентирующая строка

Небольшая строка с фактическими числами: «Срочно решить: N», «В работе: N», «Ждём ответа: N». Каждый счётчик — переход к соответствующему разделу ниже, не отдельная красивая метрика без действия. Если одной из групп нет, показывать 0 или спокойную подпись, а не придумывать элементы. Не использовать процент готовности, пока нет согласованного состава задач и правила расчёта.

### 1.3 Требует решения

Первый содержательный блок. Заголовок «Требует решения · N» (или «Срочно решить · N», если общий текст уже закреплён в продукте). В него попадают уникальные незавершённые задачи проекта, которые **заблокированы**, **просрочены** либо **имеют срок сегодня**. Это та же функция определения внимания, что и на главном экране; статус `waiting` сам по себе не делает задачу срочной. Если задача и заблокирована, и просрочена, здесь она только один раз. Не копировать одну и ту же задачу в нескольких строках этого блока.

Каждая строка содержит: маленький статус с причиной внимания; название задачи; срок, если он есть; ответственного или «Не назначен». Если доступна явная причина блокировки, показать коротко или в подробностях задачи, не угадывать причину из названия. Нажатие открывает конкретную задачу в проекте. По умолчанию 3–5 строк в зависимости от места, далее «Показать все N»/«Свернуть»; число заголовка — все элементы, не только видимые. Если срочного нет: компактное позитивное состояние «Сейчас нет задач, требующих срочного решения». У пустого состояния нет тревожной окраски.

### 1.4 Сейчас в работе

Отдельный блок с задачами `in_progress`, кроме завершённых/отменённых. Показать название, ответственного, ближайший срок при наличии, и следующее действие только если оно реально задано в данных; не генерировать «следующие шаги» по названию задачи. Задача `in_progress` может одновременно быть просроченной: она остаётся в работе, а также появляется в блоке внимания; это осмысленные разные представления одного объекта. Одинаковые ID и кликабельный переход должны быть согласованы.

При отсутствии таких задач: «Пока нет задач в работе», без фразы «В работе: пока нет задач в работе». Не подменять список задачами со статусом `todo`.

### 1.5 Ждём ответа / внешнего действия

Показывать задачи с явным статусом `waiting` (или его существующим аналогом). В строке: **чего ждём**, **от кого** (если поле есть), **ответственный внутри команды**, **с какого момента ждём** либо контрольная дата (если поля имеются). Формулировку «Ждём ответа от клиента/подрядчика» выводить только если адресат указан структурированно; при отсутствии адресата — «Ждём ответа» и название задачи.

«Ждём ответа» не равно «Заблокировано»: задача может ожидать обычного ответа, не останавливая другую работу. Ожидание попадает в «Требует решения» только по общему правилу просрочки/срока сегодня либо при явной блокировке. Если дата последующего контакта не хранится, нельзя автоматически писать «Нужно напомнить» или запускать просрочку по возрасту задачи. Отдельную механику follow-up описать после появления соответствующих полей и сценария.

Если модель пока не хранит `waiting`, отложить этот блок с честным пустым состоянием/скрытием и перечислить минимальные поля для следующей итерации. Нельзя выводить ожидание по словам «согласовать» или «получить» в названии задачи.

### 1.6 Все задачи проекта

Внизу — переход «Все задачи» и компактный список/превью задач для ориентира, если модуль задач уже существует. Показывать до 5 наиболее релевантных незавершённых записей, не превращать обзор в повтор всей таблицы задач. Завершённые задачи доступны через полный список, но не занимают верх обзора. Статусы в этом списке компактны и используют один общий компонент. Строка открывает задачу.

Если отдельной страницы задач пока нет, кнопка «Все задачи» может вести к разделу задач на этой же странице с понятным якорем; не показывать неработающий маршрут. Базовые действия «+ Добавить задачу» и изменение её состояния доступны только там, где реально реализованы и позволяют права пользователя.

## 2. Поведение карточки задачи

Клик из любого блока обзора открывает **ту же задачу**: её ID, проект, название, статус, срок, ответственный, причина блокировки/ожидания при наличии. Открытие из глобального списка должно приводить в проект с открытой задачей (`projectId` + `taskId` в URL или эквивалентный устойчивый маршрут). Обновление страницы и новая вкладка восстанавливают карточку. Если задача удалена/недоступна — сообщение и переход к доступному обзору; не открывать случайную первую задачу.

На mobile допускается полноэкранная панель, на desktop — боковая панель или страница, если существующая архитектура это поддерживает. Действие «Отметить выполненной» явно изменяет состояние, после чего счётчики и списки пересчитываются без ручных правок. Действие для закрытия панели называется «Вернуться к проекту»/«Закрыть карточку», **не** «Закрыть задачу»: последнее можно спутать с завершением работы. Пока изменение не сохранено, показать состояние выполнения; при ошибке вернуть понятную возможность повтора, не уменьшать счётчики оптимистично навсегда.

## 3. Расчёты, синхронизация и права

- Источник истины — сохранённые проекты и задачи, доступные текущему пользователю. Одни и те же функции селекции задач используются для главной страницы, проектного обзора и подробной карточки.
- Сигнал внимания: явная блокировка; либо дедлайн < now; либо дедлайн сегодня и ещё не прошёл. Завершённые/отменённые исключаются. Архивные проекты не попадают в общий блок внимания на главной; внутри архивного проекта данные можно показывать как историю, без живой тревожной окраски и активных действий, если архив read-only.
- При сроке без времени считать дедлайном конец дня в зоне агентства; не выдумывать «19:20». Метки пересчитывать при возвращении на страницу и пересечении границы суток/дедлайна.
- В пределах проекта числа внимания и списки меняются после создания, изменения, завершения задачи; глобальный счётчик на главной отражает то же состояние. При доступном live-обновлении использовать его, в MVP допустим пересчёт после мутаций и нового открытия.
- Проверять доступ к проекту и задаче на сервере, а не только скрытием ссылки. Член команды без права архивации не видит активного действия архивировать, но может видеть доступный обзор.
- Не использовать демонстрационные числа 3 или 7 как константы. Два проекта с одинаковым названием пары различаются ID и датой/площадкой.

## 4. Визуальная структура и адаптив

Desktop: рабочая колонка достаточно широкая для текста; после шапки блок решения идёт первым. Блоки «В работе» и «Ждём ответа» можно поставить рядом при ширине, где длинные названия и ответственные сохраняют читаемость; ниже — превью всех задач. Не допускать горизонтального скролла на типичном ноутбуке. На mobile — одна колонка в порядке: навигация → шапка → краткие числа → требует решения → в работе → ждём ответа → все задачи. Блоки не должны быть отдельными крупными рамками в рамке; достаточно тонкого контура/фона по брендбуку. Статусы меньше заголовков задач, как в дизайн-итерации главной. Не дублировать шапку проекта внутри каждой карточки задачи без необходимости: в детальной панели проект можно показать небольшой ссылкой.

Доступность: заголовки в логичной последовательности, интерактивные строки доступны клавиатурой, текст статуса не выражен только цветом; фокус видим; на mobile интерактивная область строки не менее 44×44 CSS px. При длинном имени проекта, адресе площадки, названии задачи или имени ответственного текст переносится, кнопки не уезжают за экран.

## 5. Пустые и пограничные состояния

| Ситуация | Поведение |
| --- | --- |
| Новый проект без задач | Вместо трёх больших пустых блоков краткое начало работы: название, дата/место и «Добавить первую задачу», если действие реализовано. |
| Задачи есть, срочного нет | Компактное спокойное сообщение; в работе и ожидания показываются по данным. |
| Нет задач в работе, но есть срочные | «Пока нет задач в работе»; не скрывать срочные и не считать это ошибкой. |
| Задача ждёт ответа и просрочена | Одна строка в срочном блоке и одна в ожиданиях; это две смысловые группы, один ID и один пункт в срочном счётчике. |
| Дата свадьбы прошла, проект активен | Статус «Завершение проекта»; задачи по закрытию продолжают работать. |
| Нет даты или места | «Дата уточняется» и отсутствие строки площадки; без фиктивных значений. |
| Проект архивирован | Статус «В архиве»; не включать задачи в глобальную срочность. |
| Загрузка / ошибка | Скелетоны или понятная ошибка с повтором; не выдавать 0 как фактические данные при загрузке. |
| Нет доступа или проект удалён | Ясное сообщение, безопасная ссылка «Мои мероприятия»; не показывать чужие сведения. |

## 6. Критерии приёмки

1. После открытия проекта организатор видит срочные решения до длинного списка задач и может перейти в конкретную задачу одним действием.
2. Глобальный счётчик и срочный счётчик проекта совпадают с общими правилами; в проекте учитываются только его уникальные задачи.
3. Завершение срочной задачи обновляет счётчики на проектном экране и главной; она пропадает из рабочих блоков, но остаётся доступна в полном списке задач.
4. Задача с состоянием `waiting` и без дедлайна появляется в «Ждём ответа», но не становится просроченной и не порождает «Нужно напомнить» без явных данных.
5. Просроченная задача `in_progress` присутствует в «Требует решения» и «В работе» как один объект; её состояние на обеих строках согласовано.
6. В мобильной панели кнопка возврата не двусмысленна, а «Отметить выполненной» работает с подтверждённым сохранением/ошибкой.
7. Архивация доступна в меню согласно правам, не как основная кнопка; проект без даты, без места и с длинным названием отображается корректно.
8. При прямом URL на задачу после обновления открывается нужный проект и нужная задача; при отсутствии доступа данные не раскрываются.
9. Экран проверен на mobile и desktop для насыщенного проекта, нового пустого проекта, проекта без срочных задач и проекта после даты мероприятия.

## 7. Что Claude Code должен сообщить перед реализацией, если поля отсутствуют

Если текущая схема не содержит `blocked`, `in_progress`, `waiting`, получателя ожидания или контрольной даты, указать конкретные отсутствующие поля и предложить минимальную миграцию/контракт. Не заменять данные угадыванием по названию задачи. Рабочий экран можно собрать по доступным задачам и статусам, честно не показывая неподдерживаемые группы до появления данных.

## 8. Продуктовый вопрос для следующего шага

Нужно отдельно решить, что является **явным решением организатора** и как фиксируется выбор клиента/подрядчика. В MVP обзор может работать на задачах и их статусах; самостоятельную сущность «решение», клиентские согласования и автоматические follow-up вводить только с описанными действиями и данными. Это не блокирует реализацию текущего обзора.
