# ТЗ для Claude Code: упакованная свадьба и быстрая ориентация

**Экраны:** «Мои мероприятия», диалог «Новая свадьба», обзор свадьбы, новая страница «Данные пары».
**Контекст:** действующие спецификации 01–06 и `docs/HANDOFF.md`. Где этот документ расходится с ними, действует он.
**Цель:** (А) организатор за пару минут заводит новую пару так, что свадьба сразу выглядит как собранный кейс с планом, данными и видимыми пробелами; (Б) открыв свадьбу, за несколько секунд понимает, что горит, что будет дальше и чего он ждёт от других.

Работа разбита на две части. **Часть I обязательна и делается первой.** Часть II — после приёмки части I, отдельными коммитами.

## 0. Что не трогать

- Правила срочности (`classifyTask`, `buildAttention`), дедупликацию задач на обзоре, пагинацию списка, права доступа и приватность личной базы подрядчиков. Новые блоки используют те же функции и тот же снимок данных.
- Существующие задачи и сроки уже созданных свадеб. Никакие миграции не должны менять их молча.
- Авторизацию, хранилище и часовой пояс — они вне этого ТЗ.
- Не добавлять кнопок и пунктов меню, за которыми нет работающего поведения (принцип спецификаций 02 и 03 сохраняется).

# Часть I. Критичное

## 1. Модель свадьбы: пара, дата, данные

### 1.1 Новые поля проекта

| Поле | Тип | Правило |
|---|---|---|
| `partner1Name`, `partner2Name` | строка до 60, nullable | Хотя бы одно имя обязательно при создании |
| `title` | строка до 100 | Как сейчас. Если организатор не менял название вручную, собирается из имён: «Анна + Максим» (или одно имя, если второго нет) |
| `titleIsCustom` | boolean | `true`, если организатор отредактировал название руками. Тогда смена имён название не пересобирает |
| `eventDate` | `YYYY-MM-DD`, nullable | Как сейчас |
| `eventDatePrecision` | `day` / `month` / `null` | `month` — известен только месяц; `eventDate` тогда хранит первое число месяца. `null` — даты нет |
| `locationName` | строка до 150, nullable | Как сейчас. В интерфейсе подпись «Город или площадка» |
| `guestsCount` | целое 1–2000, nullable | «Примерно гостей» |
| `budgetTarget` | `{ amount, currency }`, nullable | Ориентир бюджета пары. Валюта из `CURRENCIES` |
| `contacts` | массив до 4 | `{ id, name, relation, phone, email }`; `relation`: `partner` / `parent` / `planner_side` / `other`; обязательно имя и хотя бы телефон или email |
| `formatNotes` | текст до 500, nullable | «Формат и стиль» |
| `wishesNotes` | текст до 2000, nullable | «Пожелания и важное» |

Для `month`:
- в интерфейсе дата пишется как «Июнь 2027»;
- «через N дней» заменяется на «через ~N мес.»;
- сортировка «По дате» использует `eventDate` (первое число), как и сейчас;
- стадия «Завершение проекта» наступает после последнего дня месяца.

Существующие свадьбы при чтении получают `partner1Name = null`, `partner2Name = null`, `titleIsCustom = true`, `eventDatePrecision = 'day'`, если `eventDate` есть, иначе `null`. Их данные не переписываются.

### 1.2 Редактирование свадьбы

Добавь `PATCH /api/events/:id`:
- принимает любое подмножество полей из 1.1;
- возвращает свадьбу целиком;
- поле `expectedUpdatedAt` обязательно; при расхождении — `409 conflict`, запись не перезаписывается (как у задач);
- валидация и тексты ошибок те же, что при создании; ошибки полей — `422` с `fields`.

Права:
- редактировать может любой пользователь, который видит активную свадьбу (`canSeeEvent`);
- архивная свадьба — только чтение (`409 archived`);
- это решение нужно подтвердить у заказчика, см. раздел 10.

Если название не кастомное и изменились имена, сервер сам пересобирает `title`. Если в запросе пришёл `title`, сервер ставит `titleIsCustom = true`. Пустой `title` вместе с `titleIsCustom: false` возвращает автоматическое название.

### 1.3 Смена даты и сроки задач

Если в `PATCH` изменились `eventDate` или `eventDatePrecision`, ответ дополнительно содержит `dueDateReview`. Это список задач из стартового плана, срок которых был рассчитан от прежней даты (см. 3.3):

```
dueDateReview: [
  { taskId, title, currentDueDate, proposedDueDate, isManual }
]
```

Сервер **ничего не пересчитывает сам.** Интерфейс после сохранения показывает диалог «Дата свадьбы изменилась»:
- список задач с чекбоксами: старый срок → новый срок;
- задачи с `isManual: false` отмечены по умолчанию, с `isManual: true` — не отмечены и подписаны «срок меняли вручную»;
- кнопки «Обновить сроки (N)» и «Оставить как есть».

Пересчёт — `POST /api/events/:id/tasks/reschedule` с `{ taskIds, idempotencyKey }`. Завершённые и отменённые задачи в список не попадают. Если дату убрали совсем (`null`), диалог не показывается, существующие сроки остаются.

## 2. Создание свадьбы

### 2.1 Диалог «Новая свадьба»

Один диалог, два блока. Второй блок свёрнут по умолчанию.

**Основное (видно сразу):**
- «Имя» и «Имя партнёра» — два поля в одной строке на desktop, друг под другом на mobile. Плейсхолдеры «Анна» и «Максим». Ошибка, если оба пусты: «Укажите хотя бы одно имя».
- Под полями — строка предпросмотра названия: «Свадьба: Анна + Максим» и ссылка «Изменить название», которая показывает поле `title`.
- «Дата свадьбы» — переключатель из трёх вариантов: «Точная дата» (поле даты), «Только месяц» (выбор месяца и года), «Пока неизвестна». По умолчанию «Точная дата».
- «Город или площадка» — как сейчас, необязательно.
- Чекбокс «Добавить стартовый план — 13 задач», включён по умолчанию. Подпись под ним зависит от даты: «Сроки рассчитаем от даты свадьбы» / «Без даты задачи добавятся без сроков».

**«Контакты, гости, бюджет — можно заполнить позже» (раскрывается по клику):**
- один контакт: имя, кем приходится (выпадающий список), телефон, email;
- «Примерно гостей»;
- «Ориентир бюджета»: сумма и валюта.

Кнопка «Создать свадьбу» активна, когда заполнено хотя бы одно имя и нет ошибок. Всё остальное поведение диалога сохраняется: `idempotencyKey`, подтверждение закрытия с несохранёнными данными, sheet на mobile, возврат фокуса.

`POST /api/events` расширяется полями из 1.1 и флагом `applyPlan: boolean`. Старый контракт (`title` без имён) продолжает работать для совместимости тестов и демо.

### 2.2 Стартовый план при создании

Если `applyPlan: true`:
- `createEvent` применяет все 13 пунктов `TASK_CHECKLIST` через тот же механизм, что и панель «Добавить задачи»: уникальность по `(eventId, templateKey)` и `runPlan` / `planStatus` / «Повторить создание плана»;
- существующий баннер «Создаём план подготовки» остаётся рабочим, он больше не мёртвый код;
- сроки ставятся по правилам раздела 3.

Если `applyPlan: false`, задач не создаётся, `planStatus = ready`.

Панель «Добавить задачи» остаётся как есть: она показывает уже добавленные пункты как «Добавлено». `WEDDING_V1` и `applyWeddingPlan` можно оставить только для тестов, в новых свадьбах они не используются.

### 2.3 После создания

Переход на обзор с плашкой «Свадьба создана» остаётся. Сразу под шапкой организатор видит блок «Настройка свадьбы» (раздел 4) — это главное, что он должен увидеть на пустом проекте.

## 3. Сроки стартового плана: предсказуемые, а не случайные

### 3.1 Правило

Убери `Math.random()` из `suggestDueDate`. У каждого пункта `TASK_CHECKLIST` вместо `pctFrom` / `pctTo` задаётся одно из двух:
- `afterStartDays` — через сколько дней от сегодня (для раздела «Начало»);
- `beforeEventDays` — за сколько дней до свадьбы.

| Пункт | Правило | Подпись в интерфейсе |
|---|---|---|
| Заполнить бриф пары | `afterStartDays: 7` | «в первую неделю» |
| Согласовать формат свадьбы | `afterStartDays: 14` | «в первые 2 недели» |
| Определить ориентир бюджета | `afterStartDays: 14` | «в первые 2 недели» |
| Подобрать площадки | `beforeEventDays: 300` | «за 10 мес. до свадьбы» |
| Подтвердить площадку | `beforeEventDays: 270` | «за 9 мес.» |
| Определить нужных подрядчиков | `beforeEventDays: 270` | «за 9 мес.» |
| Согласовать подрядчиков | `beforeEventDays: 180` | «за 6 мес.» |
| Составить список гостей | `beforeEventDays: 180` | «за 6 мес.» |
| Отправить приглашения | `beforeEventDays: 90` | «за 3 мес.» |
| Согласовать меню | `beforeEventDays: 60` | «за 2 мес.» |
| Подготовить тайминг | `beforeEventDays: 30` | «за месяц» |
| Подготовить рассадку | `beforeEventDays: 21` | «за 3 недели» |
| Подтвердить финальный тайминг и договорённости | `beforeEventDays: 7` | «за неделю» |

Значения временные, их уточнят с организаторами. Держи их в одном месте (`server/checklist.js`), чтобы правка была одной строкой.

### 3.2 Короткий срок подготовки

Опорная дата: `eventDate` при `day`, первое число месяца при `month`. Пусть `daysLeft` — дней от сегодня до опорной даты, `maxBefore` — наибольший `beforeEventDays` (300).
- Если `daysLeft >= maxBefore + 14` — сроки ставятся по таблице.
- Иначе все `beforeEventDays` пропорционально сжимаются: `due = eventDate − round(beforeEventDays × (daysLeft − 14) / maxBefore)`, но не раньше чем `today + 14` для задач не из «Начала» и не позже даты свадьбы. Порядок задач сохраняется.
- Сроки «Начала» не позже чем за день до самой ранней задачи из других разделов.
- Дата свадьбы в прошлом или неизвестна — сроки не ставятся, как сейчас.

Функция чистая: одинаковые входные данные всегда дают одинаковые даты. Тест обязателен.

### 3.3 Происхождение срока

Добавь задаче поле `dueDateSource`: `template` / `manual` / `null`.
- Задачи плана создаются с `template`; если дата свадьбы неизвестна, срока нет и `dueDateSource = template` всё равно ставится — это значит «срок придёт из плана».
- Любое изменение `dueDate` / `dueAt` через `PATCH` задачи или правка срока в панели «Добавить задачи» до сохранения ставят `manual`.
- Задачи, существовавшие до этого ТЗ, получают `null` и в `dueDateReview` не попадают.

`isManual` в 1.3 — это `dueDateSource === 'manual'`. В `dueDateReview` попадают открытые задачи с `templateKey` вида `checklist:*` и `dueDateSource` `template` или `manual`, в том числе задачи плана без срока.

В панели «Добавить задачи» рядом с предложенной датой показывай подпись правила («за 9 мес. до свадьбы»). Общую подпись «Сроки примерные — их можно изменить» оставь.

## 4. Блок «Настройка свадьбы»

### 4.1 Шаги

Сервер считает `setup` в `getEvent` и в карточках списка, из того же снимка:

| Шаг | Готово, когда | Действие, если не готово |
|---|---|---|
| Дата свадьбы | `eventDatePrecision === 'day'` | «Указать дату» → форма данных пары, фокус на дате |
| Данные пары | оба имени и хотя бы один контакт с телефоном или email | «Заполнить» → страница «Данные пары» |
| План задач | есть хотя бы одна задача в любом статусе | «Добавить задачи» → панель чек-листа |
| Подрядчики | есть хотя бы один подрядчик свадьбы | «Выбрать» → панель подрядчиков |
| Бюджет | указан `budgetTarget` или есть хотя бы одна строка сметы | «Указать ориентир» → форма данных пары, фокус на бюджете |

```
setup: { done: 2, total: 5, steps: [ { key, done } ] }
```

Если месяц известен, а день нет, шаг «Дата свадьбы» показывается как «Известен только месяц — уточните день».

### 4.2 Отображение на обзоре

- Место: сразу после шапки, до трёх показателей.
- Заголовок «Настройка свадьбы · 2 из 5» и тонкая полоса прогресса.
- Готовые шаги — компактно, с отметкой; неготовые — с кнопкой действия.
- Когда все 5 шагов готовы, блок не показывается. Кнопки «скрыть» нет: пробелы должны оставаться видны.
- В архиве блок не показывается.

### 4.3 Пустые состояния без ложного спокойствия

Если у свадьбы нет ни одной открытой задачи:
- «Требует внимания» показывает не «Сейчас нет задач, требующих срочного действия», а «Задач пока нет» и ссылку «Добавить задачи»;
- блоки «В работе» и «Ждём ответа» сворачиваются в одну строку «Появятся, когда задачи возьмут в работу».

Текст «Сейчас нет задач, требующих срочного действия» остаётся только для свадеб, где открытые задачи есть.

### 4.4 На карточке в «Мои мероприятия»

Если `setup.done < setup.total`, вместо строки «В работе: пока нет задач в работе» показывай «Настройка: 2 из 5». Если есть задачи в работе, строка «В работе» остаётся, а настройка показывается мелкой подписью ниже. Срочный блок карточки не меняется.

## 5. Блок «Дальше» на обзоре

### 5.1 Что попадает

- Открытые задачи со статусом `todo`, не показанные в «Требует внимания».
- Срок с завтрашнего дня по `today + 14` включительно, в поясе пространства (та же функция дат, что у срочности).
- Сортировка: по сроку, затем `createdAt`, затем `id`.
- Приоритет дедупликации расширяется: «Требует внимания» → «Ждём ответа» → «В работе» → «Дальше». Задачи `in_progress` и `waiting` в «Дальше» не попадают никогда.

Сервер отдаёт готовый список `upcoming` в `GET /api/events/:id`, а не только клиент вычисляет его: так число на обзоре и на карточке списка не разойдутся.

### 5.2 Отображение

- Место: после «Требует внимания», до «В работе» / «Ждём ответа».
- Заголовок «Дальше · 14 дней · N».
- Строка: название, срок в формате «Завтра», «Пт, 3 окт.» или «через 5 дней», ответственный.
- Лимит строк — общий модуль `breakpoints.js` (5 / 3), затем «Показать все N» / «Свернуть».
- Если в 14 днях ничего нет, но есть более поздняя открытая задача со сроком: одна строка «Ближайший срок — {название}, {дата}».
- Если открытых задач со сроком нет вообще: «Задач со сроком нет». При свадьбе без даты добавь «— укажите дату свадьбы, и задачи плана получат сроки».

Три показателя вверху не меняются, четвёртого не добавлять.

### 5.3 На карточке списка

Под строкой «В работе» добавь «Дальше: {название} · {дата}» для ближайшей задачи из `upcoming`. Строку не показывать, если `upcoming` пуст или свадьба в архиве.

## 6. Критерии приёмки части I

1. Создать свадьбу «Анна» + «Максим», точная дата через 12 месяцев, стартовый план включён. На обзоре: название «Анна + Максим», 13 задач, блок «Настройка свадьбы · 2 из 5» (дата и план готовы), в «Дальше» — «Заполнить бриф пары» через 7 дней.
2. Повторить создание с тем же `idempotencyKey` — одна свадьба, 13 задач.
3. Открыть панель «Добавить задачи» дважды — предложенные даты не меняются между открытиями и совпадают с таблицей 3.1.
4. Создать свадьбу через 60 дней — все сроки между `today` и датой свадьбы, порядок по таблице сохранён, нет срока позже свадьбы.
5. Создать свадьбу «Пока неизвестна» — задачи без сроков, «Дальше» с подсказкой про дату. Через редактирование указать дату — появляется диалог «Дата свадьбы изменилась», который предлагает **поставить** сроки всем открытым задачам плана (`currentDueDate: null`, все отмечены).
6. После «Обновить сроки» у этих задач сроки совпадают с таблицей 3.1, `dueDateSource = template`.
7. Вручную поменять срок одной задачи плана, затем сдвинуть дату свадьбы на месяц. В диалоге эта задача не отмечена и подписана «срок меняли вручную», остальные отмечены. После «Обновить сроки» изменились только отмеченные.
8. Отредактировать имена при автоматическом названии — название пересобралось. Отредактировать название вручную, затем имена — название не изменилось.
9. Два окна: сохранить в одном, затем в другом — второе получает `409` и сообщение «Данные изменил кто-то другой. Обновите страницу», ничего не перезаписано.
10. Свадьба без задач: нет текста «нет задач, требующих срочного действия»; есть «Задач пока нет».
11. Все пять шагов настройки выполнены — блок настройки исчез и на обзоре, и на карточке.
12. Задача `todo` со сроком через 3 дня видна в «Дальше» и на карточке списка; та же задача, переведённая в `in_progress`, уходит в «В работе» и из «Дальше» пропадает.
13. Существующие демо-свадьбы открываются без ошибок, их задачи и сроки не изменились.
14. 375 и 1440 px без горизонтальной прокрутки, включая длинные имена.

Тесты `node:test`: расчёт сроков (обычный, сжатый, без даты, месяц), `setup`, `upcoming` и дедупликация с ним, `PATCH /api/events/:id` (права, архив, `409`, пересборка названия), `dueDateReview` и `reschedule` (идемпотентность, ручные сроки).

# Часть II. Важное

## 7. Страница «Данные пары» и шапка обзора

### 7.1 Страница

- Маршрут `/events/:id/profile`. Работает после перезагрузки и в новой вкладке.
- Разделы: «Пара» (имена, название), «Дата и место», «Контакты» (до 4, добавить / удалить), «Гости и бюджет», «Формат и пожелания».
- Режим просмотра по умолчанию. Кнопка «Редактировать» переводит все разделы в форму; «Сохранить» / «Отмена». Сохранение — `PATCH` из 1.2.
- Телефон — ссылка `tel:`, email — `mailto:`.
- В архиве кнопки редактирования нет.
- Кнопка «← Вернуться к свадьбе».

Пункт «Редактировать данные» в меню ⋮ на обзоре ведёт сюда сразу в режиме редактирования. Это закрывает пробел, отмеченный в HANDOFF.

### 7.2 Связь с задачей «Заполнить бриф пары»

На карточке задачи с `templateKey = checklist:start-brief` показывай ссылку «Открыть данные пары →». Если шаг «Данные пары» уже готов, добавь подсказку «Данные пары заполнены — можно отметить задачу выполненной». Автоматически задачу не закрывать.

### 7.3 Шапка обзора

Под названием и стадией, одной строкой с переносом:
- дата (или «Июнь 2027», или «Дата уточняется») и «через N дней»;
- место;
- «~120 гостей», если указано;
- первый контакт: имя и телефон ссылкой;
- ссылка «Данные пары →».

Показывать только то, что заполнено. Не показывать пустые подписи вроде «Гости: —».

## 8. Сводка, быстрые действия, язык

### 8.1 Сводка «Подрядчики и смета»

Компактный блок после задачных блоков:
- «Подрядчики: подтверждено 3 из 5»;
- «Смета: 1 240 000 ₽ из 1 500 000 ₽» (второе число — `budgetTarget`, если валюта совпадает; при другой валюте — только итог и подпись «Ориентир в другой валюте»);
- «Без цены: 2» — ссылка на смету.
- Кнопки «Подрядчики» (раскрывает существующий список ниже) и «Смета →».

Данные — из существующих `GET …/vendors` и `GET …/budget`, отдельной загрузкой, как сейчас. Ссылку «Открыть все задачи →» перенеси в конец задачных блоков как обычную текстовую ссылку, а не кнопку посреди страницы.

Итоговый порядок обзора: шапка → «Настройка свадьбы» → три показателя → «Требует внимания» → «Дальше» → «В работе» / «Ждём ответа» → «Все задачи →» → «Подрядчики и смета».

### 8.2 «Пора напомнить» в «Ждём ответа»

Задача `waiting` с `followUpAt <= today` получает в строке мягкий бейдж «Пора напомнить» (нейтральный тон, не красный) и стоит в блоке первой. Во «Требует внимания» и в счётчики она по-прежнему не попадает (решение итерации 3 сохраняется).

### 8.3 Быстрое «Выполнено»

В строках «Требует внимания», «Дальше» и «В работе» на обзоре добавь отдельную кнопку-чекбокс «Отметить выполненной» слева от текста, цель не меньше 44 px. Строка остаётся ссылкой на задачу, кнопка не вложена в ссылку.
- После нажатия строка исчезает, внизу экрана тост «Задача выполнена» с кнопкой «Отменить» на 6 секунд. «Отменить» вызывает существующее восстановление задачи.
- Счётчики и блоки пересчитываются из нового снимка, как после выполнения в карточке задачи.
- В архиве кнопки нет.

### 8.4 Диалог подтверждения вместо `window.confirm`

Сделай общий компонент подтверждения на нативном `<dialog>` и замени им все `window.confirm`:
- **Убрать подрядчика из свадьбы:** текст «Убрать «{имя}» из этой свадьбы? Личная запись в вашей базе сохранится.» и выбор для строки сметы — радиокнопки «Удалить строку из сметы» / «Оставить как отдельный расход» (по умолчанию второе). Кнопки «Убрать» и «Отмена».
- **Архив:** «Переместить «{название}» в архив? Вернуть можно в любой момент из вкладки «Архив».» Кнопки «В архив» и «Отмена».

### 8.5 Единый словарь

В интерфейсе объект везде называется **«свадьба»**. Название раздела «Мои мероприятия» остаётся как зонтик для будущих типов событий. Идентификаторы в коде не переименовывать.

| Было | Стало |
|---|---|
| Свадебные проекты вашей команды | Свадьбы вашей команды |
| Название проекта | Название свадьбы (поле видно только по ссылке «Изменить название») |
| Открыть проект → | Открыть свадьбу → |
| Проект не найден или доступ к нему закрыт | Свадьба не найдена или доступ к ней закрыт |
| Не удалось загрузить проект | Не удалось загрузить свадьбу |
| Проект перемещён в архив / возвращён в активные | Свадьба перемещена в архив / возвращена в активные |
| Действия с проектом | Действия со свадьбой |
| Вернуться к проекту | Вернуться к свадьбе |
| Нет права создавать проекты | Нет права создавать свадьбы |
| Завершение проекта (стадия) | После свадьбы |

Пройди поиском по `web/js` и серверным сообщениям об ошибках, которые показываются пользователю, и приведи остальные вхождения к тому же словарю.

## 9. Критерии приёмки части II

1. Со свадьбы открыть ⋮ → «Редактировать данные», добавить контакт и гостей, сохранить — шапка обзора показывает гостей и телефон ссылкой, шаг «Данные пары» готов.
2. Смета с итогом в той же валюте, что ориентир: сводка показывает «X из Y». В другой валюте — только итог и подпись.
3. Задача `waiting` с прошедшей контрольной датой — первая в «Ждём ответа» с бейджем «Пора напомнить»; счётчик «Требует внимания» не изменился.
4. Быстрое «Выполнено» → строка исчезла, счётчики пересчитались; «Отменить» вернул задачу в прежний статус и блок.
5. Убрать подрядчика с «Оставить как отдельный расход» — строка сметы осталась ручной, итог не изменился. С «Удалить строку» — строки нет.
6. Поиск по интерфейсу не находит слов «проект» / «проекта» в пользовательских текстах, кроме названия раздела задач, если оно так утверждено.
7. Клавиатура: все новые кнопки и диалоги доступны с Tab, Escape закрывает диалог, фокус возвращается на кнопку-источник.

## 10. Нужно решить заказчику (не угадывать)

1. Кто может редактировать данные свадьбы: любой участник с доступом (так в этом ТЗ) или только owner.
2. Горизонт блока «Дальше»: 14 дней или другой.
3. Значения сроков стартового плана из таблицы 3.1.
4. Нужны ли поля «источник заявки» и «гонорар организатора» — в этом ТЗ их нет сознательно.
5. Словарь: «свадьба» во всём интерфейсе и «Мои мероприятия» как название раздела — подтвердить.
