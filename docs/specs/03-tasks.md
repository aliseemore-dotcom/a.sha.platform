# Задачи мероприятия — единое ТЗ v1 для Claude Code

**Раздел:** «Задачи» внутри конкретного мероприятия.  
**Входы:** «Открыть все задачи» из обзора, прямая ссылка на задачу из списка мероприятий/обзора, создание первой задачи из пустого проекта.  
**Цель:** организатор создаёт, назначает, отслеживает и завершает задачи одного мероприятия. Он отличает собственную работу от ожидания ответа, блокировки и просроченного срока. Все изменения сразу согласуются с обзором проекта и главной страницей.  
**Визуальная основа:** брендбук Soft Editorial Glass и утверждённая дизайн-итерация экрана «Мои мероприятия». Этот документ определяет поведение, а брендбук — базовые токены.

## 0. Объём первой реализации

Реализовать рабочий список задач проекта, создание/редактирование, просмотр подробностей, изменение состояния, назначение ответственного, срок, ожидание ответа, блокировку, завершение и восстановление завершённой задачи. Переиспользовать существующие компоненты и модели, не строить вторую независимую базу задач для этой страницы.

Не включать в этот этап шаблоны свадебных планов, вложенные подзадачи, комментарии, вложения, интеграцию с мессенджерами, автоматическую отправку сообщений или согласования с клиентом. Их отсутствие не должно порождать неработающие кнопки. Задачи привязаны к существующему `projectId`; если пользователь не имеет доступа к проекту, список и прямой URL недоступны.

**Согласованность документов:** общие правила срочности, рабочих статусов и часового пояса совпадают с ТЗ главной и обзора. Контрольная дата ожидания (`followUpAt`) в этом MVP является видимым полем и доступна в фильтре «Проверить ответ»; она **не создаёт автоматически глобальную срочность или системное уведомление**. Для сигнала «Пора напомнить» позже понадобятся отдельное действие фиксации контакта/переноса контроля и изменение правил главной и обзора. Не выдавать контрольную дату за `dueAt`.

## 1. Навигация и структура экрана

- Сохранить постоянный контекст проекта: ссылка «← Обзор проекта», название мероприятия, дата/площадка компактно. «Все задачи» как заголовок раздела. Если в приложении уже есть навигация по проекту, встроить раздел в неё.
- Под заголовком действия: **«+ Добавить задачу»**, поиск, фильтры и сортировка. Форма добавления должна быть доступна на mobile без горизонтального скролла.
- Основное содержимое — один список с вкладками/сегментами **«Открытые»** и **«Завершённые»**. «Открытые» включает `todo`, `in_progress`, `waiting`, в том числе заблокированные; «Завершённые» включает `done`. Отменённые, если поддерживаются, показывать отдельным фильтром «Отменённые», не смешивать с выполненными.
- Каждая задача отображается **ровно одной строкой** в соответствующей вкладке. Не повторять её отдельной карточкой наверху того же списка. Срочность и рабочее состояние представлены признаками в одной строке.
- Строка показывает название, рабочий статус, индикатор внимания при наличии, ответственного, срок выполнения и краткий адресат ожидания при `waiting`. На desktop достаточно колонок, на mobile порядок: название → маленькие статусы → ответственный/срок; длинный текст переносится. Не повторять название проекта в каждой строке.
- Нажатие строки открывает карточку задачи; чекбокс для быстрого завершения допустим только если не приводит к случайному клику при открытии строки и есть возможность восстановить. Приоритет — надёжное действие внутри карточки.

### 1.1 Пустые состояния

Нет задач: «Здесь пока нет задач» + рабочая кнопка «Добавить первую задачу». Открытых нет, но есть завершённые: «Все текущие задачи выполнены» + переход к завершённым и добавление. Фильтр/поиск без результатов: «По вашему запросу задач нет» + «Сбросить фильтры», не показывать onboarding. Ошибка загрузки: сообщение и «Повторить», не считать это пустым списком.

## 2. Модель данных и статусы

Использовать существующие имена и API, сопоставив смысл с таблицей. Если части полей нет — предложить минимальное расширение существующей модели и выполнить его согласованно с клиентом/сервером, не хранить важные статусы только в состоянии браузера.

| Поле | Тип/правило | Назначение |
| --- | --- | --- |
| `id`, `projectId` | устойчивые идентификаторы | Прямой URL, связь с проектом, проверка прав. |
| `title` | обязательная строка, trim, 1–200 символов | Краткое проверяемое действие; не создавать пустые/состоящие из пробелов задачи. |
| `description` | необязательный текст | Детали задачи, сохранять переносы; выводить безопасно, без HTML из ввода. |
| `status` | `todo`, `in_progress`, `waiting`, `done` (и `cancelled`, если уже поддерживается) | Единственный рабочий статус в момент времени. |
| `assigneeId` | nullable, член команды с доступом к проекту | Внутренний ответственный. Пустое значение показывать «Не назначен». |
| `dueAt` | nullable, дата или дата+время с зоной | Когда должно быть выполнено действие; источник просрочки. |
| `isBlocked`, `blockedReason` | отдельный признак и причина | Причина остановки работы, независима от `status` и срока. |
| `waitingFor` | nullable, структурированная роль/имя/контакт, если модель поддерживает | От кого ожидается ответ; не угадывать по названию. |
| `followUpAt` | nullable, дата или дата+время | Когда вручную проверить ответ; отдельно от дедлайна. |
| `createdAt`, `updatedAt`, `completedAt`, `completedBy` | системные поля при наличии | Сортировка, прозрачность завершения. |

Для `waitingFor` в MVP можно использовать простое текстовое поле «От кого ждём» (например, «Флорист»), если нет общей базы подрядчиков; это не должно создавать фиктивную связанную запись подрядчика. При появлении связанного контакта поле может ссылаться на него. Не превращать текст в автоматическую переписку.

**Статус и блокировка:** блокировка — отдельный признак. Задача может быть `in_progress` + blocked или `waiting` + blocked. Не добавлять «Просрочено» как значение `status`: просрочка вычисляется по `dueAt` и текущему времени. Переход в `done` снимает задачу с рабочих счётчиков; при восстановлении возвращает предыдущий рабочий статус, если он сохранён, иначе `todo`. Снять активную блокировку при завершении, сохранив историческую причину в истории, если она имеется. Не создавать вторую активную задачу при восстановлении.

## 3. Внимание и время

Единая функция для всех экранов проекта:

```text
attention(task, now, agencyTimezone) =
  task not in {done, cancelled}
  AND (task.isBlocked OR task.dueAt < now OR task.dueAt is today)
```

Если `dueAt` хранится только как дата, считать окончанием срока конец этого дня в часовом поясе агентства. Сегодня до наступления времени — «Сегодня · HH:mm»; после — «Просрочено с HH:mm» или «Просрочено N дней» по согласованному общему форматтеру. Завтра не просрочено. Смена даты/времени обновляет метки при возвращении на страницу и без ожидания следующей ручной перезагрузки. Не применять браузерную зону отдельно от главной/обзора.

Если задача одновременно blocked, waiting и overdue, в строке показать не больше двух компактных сигналов: один основной признак внимания и один рабочий статус. В карточке подробностей доступны все основания. Счётчик внимания считает `taskId` один раз. Списки и карточки главной/обзора используют тот же ID и вычисления.

`followUpAt` не меняет метку «Просрочено». Если контрольная дата наступила, в разделе задач показать информационный текст «Проверить ответ» и дать фильтр по таким ожидающим задачам; не прибавлять их к счётчику «Требует внимания» на других экранах в этой версии. Дата контроля может быть вчера, но срок самой задачи — завтра: строка не должна называться просроченной.

## 4. Список: поиск, фильтры, сортировка

По умолчанию открыть вкладку «Открытые», сортировка **«Сначала требующие внимания»**: заблокированные, затем просроченные по давности срока, затем с дедлайном сегодня по времени, затем остальные по ближайшему `dueAt`; без срока в конце; устойчивый вторичный ключ `createdAt`, затем `id`. Совпадение блокировки и просрочки не создаёт два ряда. Если существующая главная использует иной порядок двух первых групп, выровнять общую функцию и сохранить единый порядок.

Поиск по `title` и `description` внутри **только текущего проекта**, без учёта регистра; не раскрывать данные других проектов. Минимальные фильтры: ответственный («Все»/конкретный/«Не назначен»), рабочий статус, «Требует внимания», «Без срока», «Проверить ответ» (для `waiting` с `followUpAt <= now`). Несколько фильтров соединяются через AND. Кнопка «Сбросить» возвращает параметры по умолчанию. Показывать число найденных задач, отдельно от общего числа задач. Если пользователь выбрал статус `done`, переключить/объяснить вкладку, а не молча получить пустоту; можно ограничить фильтр статуса значениями выбранной вкладки.

Варианты сортировки: «Сначала требующие внимания» (default), «По сроку» (возрастание, без срока в конце), «По дате создания» (новые сверху). Завершённые по умолчанию по `completedAt` убыванию, при отсутствии поля — по `updatedAt`; не использовать «срочность» для выполненных. Параметры поиска/фильтра/вкладки сохранять в URL, чтобы ссылка на список и возврат из карточки восстанавливали контекст. Прямой URL без параметров использует defaults. При большом списке серверная пагинация или постепенная загрузка, без неограниченной отрисовки сотен строк.

## 5. Создание и редактирование

### 5.1 Форма создания

Открывается по «+ Добавить задачу» из проекта или из пустого состояния. Поля первой версии: обязательное **«Что нужно сделать»**; необязательные описание, ответственный, срок выполнения, рабочий статус (по умолчанию `todo`). Дополнительные поля появляются контекстно: при `waiting` — «От кого ждём» и «Когда проверить ответ»; при включении «Заблокировано» — обязательная причина блокировки (короткий текст). Не заставлять пользователя заполнять все поля ради быстрой задачи.

Срок выбирается как дата и необязательное время. Явно различить в интерфейсе «Срок выполнения» и «Контроль ответа». Если время срока не задано, использовать date-only, не сохранять тихо 00:00. Контрольная дата доступна только для `waiting` и не должна наступать после завершения задачи. Если адресат ожидания неизвестен, поле может остаться пустым с подписью «Не указан»; не подменять его ответственным команды.

Сохранить: валидировать, создать ровно одну запись, закрыть форму, показать её в правильной вкладке/позиции и обновить счётчики. После ошибки данные формы остаются и есть повтор. Защититься от двойного нажатия «Сохранить»; не создавать дубликат при повторном запросе. «Отмена» закрывает пустую форму сразу, а при введённых несохранённых данных предупреждает о потере изменений.

### 5.2 Редактирование и переходы состояний

Карточка задачи показывает все фактические поля и действия: «Редактировать», «Отметить выполненной» либо «Вернуть в работу». Изменение статуса `todo → in_progress → waiting` не обязательно линейно: пользователь может выбрать нужное состояние напрямую. При переходе **из** `waiting` убрать активный контроль ожидания и адресата из рабочей карточки; если есть аудит, сохранить их там. Если аудит отсутствует, заранее предупредить в форме, что скрываемые данные будут удалены, и не очищать их случайно до сохранения. При переходе в `done` записать `completedAt`, снять активное ожидание/блокировку; при возврате статус `todo` или явно сохранённый предыдущий. Изменения ответственного, срока и блокировки немедленно меняют список и счётчики после подтверждения сервера.

Если задача выполнена, в карточке видны время и человек завершения, если система хранит их. Для отменённых задач, если такой статус уже есть, предоставить восстановление по правилам текущей модели. Физическое удаление задачи в MVP не требуется; не ставить кнопку удаления как главное действие без сценария восстановления.

### 5.3 Прямой URL и закрытие карточки

Маршрут включает проект и задачу: использовать существующий route shape, но URL должен работать после перезагрузки и в новой вкладке. Если задача из другого проекта или доступ отозван — сервер запрещает раскрытие. Mobile: карточка полноэкранная или как существующий шаблон; desktop: боковая панель/страница, если сохраняется список. Действие закрытия называется **«Вернуться к задачам»** при входе из списка и **«Вернуться к проекту»** при входе из обзора, исходя из реального контекста. «Закрыть задачу» для выхода из панели запрещено из-за двусмысленности. Возврат сохраняет поиск/фильтры и позицию списка, насколько позволяет приложение.

## 6. Доступ и согласованность

По умолчанию список видят участники с доступом к проекту. Возможность создавать/редактировать/завершать/назначать проверять на сервере по существующим ролям; нельзя считать, что скрытая кнопка защищает данные. Ответственным можно назначить только пользователя с доступом к проекту. Если пользователь утратил доступ, показать безопасный возврат к «Моим мероприятиям». В архивном проекте список доступен как история; редактирование/создание выключить, если архив в текущей модели read-only. После восстановления проекта применить обычные права.

Сервер — источник истины. После каждой мутации инвалидировать/обновить данные задачи, список, обзор и счётчики главной через существующий механизм. Не поддерживать отдельные ручные числа `urgentCount` на разных страницах. При конкурентных изменениях показать свежую запись и предупреждение, не затереть незаметно правку другого участника. Если приложение поддерживает live updates, использовать их; иначе сверять при возвращении на экран.

## 7. Адаптив и визуальный стиль

Рабочий раздел спокойнее обзора: светлый фон, одна ясная таблица/список, минимум цветных поверхностей. Статусы компактны по принятой итерации (на mobile порядка 11–12 px с небольшими внутренними полями), название задачи доминирует. Красный — локальный знак просрочки/блокировки, не красная рамка вокруг каждой строки. Тонкие разделители, видимый hover/focus, понятные disabled/loading состояния. На mobile фильтры доступны в компактной панели, выбранные фильтры можно снять по отдельности; список остаётся в одну колонку без горизонтальной прокрутки. Области нажатия от 44×44 CSS px, текст статуса доступен без различения цвета. Поддержать длинные названия, отсутствие срока и ответственного.

## 8. Приёмочные сценарии

1. Из обзора «Мария + Илья» по «Открыть все задачи» открываются задачи только этого проекта; возврат ведёт обратно к обзору.
2. Создание «Согласовать меню» только с названием создаёт `todo` без фиктивного срока и ответственного; после назначения задача отображает правильного человека.
3. `in_progress` задача со вчерашним `dueAt` показана в списке одной строкой с рабочим статусом и просрочкой; глобальный и проектный счётчики включают её один раз.
4. `waiting` задача с адресатом «Флорист», `followUpAt` вчера и `dueAt` завтра попадает в фильтр «Проверить ответ», но не имеет метки «Просрочено» и не попадает в глобальную срочность только из-за контроля.
5. Если у той же ожидающей задачи `dueAt` вчера, она просрочена по сроку выполнения и одновременно остаётся `waiting`; на обзоре её основная строка одна.
6. Завершение срочной задачи удаляет её из открытых и рабочих счётчиков, переносит в завершённые. Восстановление возвращает ту же запись и корректно пересчитывает показатели.
7. Блокировка с причиной и сроком сегодня не дублирует задачу в списке и счётчике; причина видна в карточке.
8. Поиск/фильтры/сортировка действуют только в текущем проекте, сохраняются при открытии и закрытии карточки, сброс возвращает исходный список.
9. Date-only срок не становится просроченным в 00:00 начала указанного дня; отображается без придуманного часа.
10. Создание с двойным нажатием, ошибка сохранения, конкурентное изменение и потеря доступа не создают дублей и не показывают чужие данные.
11. Раздел проверен на desktop и mobile с 0, 1 и большим числом задач, длинным названием, пустыми датами, ожиданием ответа и архивным проектом.

## 9. Перед запуском работы в коде
