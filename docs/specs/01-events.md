# Экран 01 «Мои мероприятия» — спецификация для Claude Code

Версия: 1.0 · 23 сентября 2026  
Статус: готово к сборке первого экрана MVP  
Визуальный источник: `Soft_Editorial_Glass_brandbook.pdf`, версия 1.1. Визуальные токены и компоненты брать из него; требования к данным и поведению на этой странице — из данного документа.

## 0. Контекст и границы

Продукт — рабочее пространство **профессионального организатора свадеб**. Первый экран после входа помогает управлять несколькими свадебными проектами. Пользователь выбрал: **в первом MVP создаются только свадьбы**. Не показывать селектор других типов событий и не добавлять фиктивные варианты.

Главный вопрос экрана: **«Какой проект требует моего внимания и почему?»** Человек должен за 10–15 секунд найти нужную свадьбу и открыть её. Второе ключевое действие — создать новую свадьбу.

Экран не является детальным обзором одной свадьбы. Задачи, подрядчики, смета, гости, файлы и тайминг редактируются **внутри проекта**. Здесь показывается только их краткий, вычисляемый сигнал, если для него уже есть данные. Не строить «универсальный CRM дашборд» из вымышленных KPI.

Роли MVP: `owner` (владелец рабочего пространства) и `member` (участник команды). Если система ролей ещё не реализована, применять правило видимости: пользователь видит только проекты своего рабочего пространства, доступ к которым ему выдан; интерфейс не должен полагаться только на клиентскую фильтрацию. Создавать проект вправе `owner` и участник с явным правом `event:create`.

## 1. Маршруты и поведение после входа

| Событие | Результат |
|---|---|
| Успешный вход | Открыть `/events` (или существующий маршрут списка проектов); вкладка «Активные» |
| Клик по карточке/названию | Открыть `/events/:eventId/overview` в текущей вкладке |
| Клик по пункту срочных дел | Открыть связанный проект и соответствующий объект; если детальный deep link ещё не готов — обзор проекта с фокусом на блоке «Срочно решить» |
| Успешное создание | Открыть обзор созданного проекта; системное подтверждение «Свадьба создана» |
| Возврат браузером | Сохранить вкладку, поиск и сортировку через URL query; восстановить положение списка, если возможно без сложного состояния |
| Прямой переход без авторизации | Перенаправить на вход с сохранением безопасного `returnTo` |

`/events` — логический маршрут; адаптировать его к существующему роутеру проекта. Не создавать параллельную систему маршрутизации.

## 2. Структура страницы

Порядок DOM и чтения должен соответствовать порядку ниже.

1. **Шапка продукта:** текстовое рабочее название/логотип только если он предоставлен; навигация пользователя и выход. Не придумывать окончательный бренд или знак. На мобильном шапка компактная.
2. **Заголовок «Мои мероприятия»** и пояснение `Свадебные проекты вашей команды` (пояснение можно скрыть на узком экране).
3. **Главное действие «+ Создать свадьбу».** Одна явно доминирующая кнопка в шапке страницы. Не называть её «Новый проект» в одном месте и «Создать мероприятие» в другом.
4. **«Требует внимания»:** общий список открытых проблем по доступным активным проектам. Показывать только при наличии таких элементов. Заголовок `Требует внимания · N`, первые пять строк; если их больше, кнопка `Показать ещё` раскрывает следующие 20 строк. Повторное нажатие догружает следующие 20 через сервер. Не загружать все срочные элементы сразу и не оставлять неработающий CTA.
5. **Панель списка:** вкладки `Активные (N)` / `Архив (N)`; поиск `Найти свадьбу`; сортировка `По дате` / `По вниманию`. По умолчанию активные, по дате. Счётчики отражают все доступные проекты данной вкладки до поискового фильтра, чтобы смысл числа не менялся при вводе.
6. **Карточки свадеб:** одна или две колонки в зависимости от ширины; порядок задан выбранной сортировкой. В каждом проекте: название, дата или `Дата уточняется`, место при наличии, состояние, один главный повод зайти (если есть), до двух элементов «Сейчас в работе» и явное действие `Открыть проект`. Не выводить процент готовности без утверждённой формулы.
7. **Пагинация/«Показать ещё»:** если активных проектов более 20. Поиск и сортировка должны работать по всему набору доступных проектов, а не только по уже загруженным 20.

Никаких кнопок команды/настроек как пустых иконок. Если эти функции пока не существуют, не показывать их. Не добавлять копирайт в нижнюю часть рабочей страницы только ради заполнения пустоты.

### Карточка проекта — точный состав

```
[Дата: 14 июн 2027]  [Состояние: Активен]
Анна + Максим
Свадьба · Загородная площадка «Лес» [если место известно]

Срочно: до завтра подписать договор с площадкой [только если правило срочности выполнено]
В работе: меню; подбор ведущего [только реальные активные элементы]

Открыть проект →
```

Карточка целиком кликабельна только если внутри нет других самостоятельных ссылок и кнопок; не вкладывать интерактивные элементы друг в друга. При наличии вложенных действий кликабельно только название и явная ссылка. Нельзя выводить одновременно `Срочно` и спокойный статус `Всё по плану` для одной карточки.

Если нет ни срочных, ни активных элементов: `Пока нет задач в работе` без искусственного «Всё готово». Если дата прошла, но проект активен: `Дата прошла · проект активен`; отрицательный обратный отсчёт не показывать. Архивная карточка содержит дату, название и `В архиве`, без активных дедлайнов.

## 3. Модель данных для этого экрана

Использовать существующую модель проекта, если она есть. Ниже — контракт данных, а не обязательные имена колонок БД. Сервер отдаёт только доступные пользователю проекты и агрегаты по ним.

```ts
type EventListItem = {
  id: string;
  title: string;                 // «Анна + Максим», 1–100 символов после trim
  kind: 'wedding';               // единственный тип MVP
  eventDate: string | null;      // YYYY-MM-DD, дата площадки, без времени
  locationName: string | null;
  lifecycle: 'active' | 'archived';
  coverUrl: string | null;       // только загруженное пользователем фото
  createdAt: string;            // ISO timestamp
  updatedAt: string;            // ISO timestamp
  urgentCount: number;          // вычислено на сервере, не редактируется вручную
  urgentPreview: AttentionItem | null;
  activePreview: Array<{ id: string; title: string }>;// максимум 2
};

type AttentionItem = {
  id: string;                   // стабильный id исходной задачи/решения
  eventId: string;
  eventTitle: string;
  title: string;                // фактическое название работы
  kind: 'overdue' | 'blocked' | 'due_today' | 'follow_up_due';
  dueAt: string | null;         // ISO timestamp, если есть срок со временем
  ownerName: string | null;
  targetUrl: string;            // только безопасный внутренний маршрут
};
```

Минимальные поля исходной задачи, откуда выводятся агрегаты: `id`, `eventId`, `title`, `status`, `dueAt`, `followUpAt`, `assigneeId`, `updatedAt`. Статусы задачи: `planned`, `in_progress`, `waiting`, `blocked`, `done`, `cancelled`. **Просрочено — вычисляемый признак**, а не статус жизненного цикла. `waiting` означает ожидание ответа/материала; `followUpAt` — дата повторного контакта. Оплата — отдельная сущность; `paid` не является статусом задачи. Не включать платежи в сигнал «Требует внимания» до согласованной модели платежей.

Пример ответа списка (данные демонстрационные, не хардкодить в продукт):


## 4. Автоматизация и точные правила внимания

### 4.1 Какие элементы попадают в «Требует внимания»

Учитывать только задачи активных доступных пользователю проектов, кроме `done` и `cancelled`. Один объект может подходить под несколько условий, но показывается **один раз** по условию с наивысшим приоритетом.

| Приоритет | Вид | Условие | Текст метки |
|---|---|---|---|
| 1 | `overdue` | Есть `dueAt`, момент срока прошёл, задача не завершена | `Просрочено` + длительность/дата |
| 2 | `blocked` | `status = blocked` | `Заблокировано` |
| 3 | `due_today` | `dueAt` попадает в текущий календарный день рабочей зоны, срок ещё не прошёл | `Сегодня` + время, если задано |
| 4 | `follow_up_due` | `status = waiting`, `followUpAt` сегодня или раньше, нет более высокого условия | `Нужно напомнить` |

Ровно в момент наступления срока объект меняет `due_today` на `overdue`. Задачи с датой без времени становятся просроченными **на следующий календарный день**, а не в 00:00 дня дедлайна. Для этого тип срока должен хранить точность (`date` или `datetime`) или эквивалентный признак; не угадывать её по строке. Для сравнения использовать часовой пояс рабочего пространства, по умолчанию `Europe/Moscow` **только для тестового стенда**, если рабочее пространство ещё не хранит настройку. В продакшене не подменять установленную зону устройства или агентства московским временем без явной настройки.

Сортировка общего списка внимания: вид по приоритету выше → ближайший/самый давно прошедший срок (`overdue` сначала более старый) → дата свадьбы (раньше первой, неизвестная последней) → стабильный `id`. `urgentCount` карточки — число всех подходящих объектов проекта, а не число видимых строк. `attentionTotal` — сумма по всем доступным активным проектам. Не выводить `0 срочных` отдельной карточкой каждому проекту.

### 4.2 «Сейчас в работе»

Брать задачи с `status = in_progress`, кроме попавших в `attention` этой карточки. Упорядочить по ближайшему сроку, затем `updatedAt` по убыванию; максимум две в превью. Пустое превью не заполнять шаблонными словами вроде «декор» или «меню». `planned` не считать «в работе».

### 4.3 Автоматическое обновление

- После изменения задачи в другой вкладке/участником обновить агрегаты при возврате фокуса на страницу и по явному `Обновить`, если используется ручной запрос. Если уже есть realtime, использовать его; не вводить новое соединение ради одного экрана.
- При переходе календарного дня или наступлении времени `dueAt` обновить локальное отображение и запросить агрегаты. Таймер нужно очищать при размонтировании; сервер остаётся источником истины.
- После создания, архивирования или восстановления проекта обновить список и счётчики без полной перезагрузки окна.
- Не делать автоматических отправок клиенту или подрядчикам с этого экрана. Напоминание здесь — сигнал для организатора.

## 5. Создание свадьбы с этого экрана

Кнопка открывает доступный с клавиатуры диалог `Новая свадьба` (на узком экране — полноэкранный sheet или отдельный маршрут). Поля:

| Поле | Правило |
|---|---|
| `Название проекта` | Обязательно, 1–100 символов после trim. Placeholder: `Например, Анна + Максим`. Не требовать имена двух людей по отдельности |
| `Дата свадьбы` | Необязательно. Если неизвестна, явное `Дата пока неизвестна`; `eventDate = null`. Дата в прошлом допускается, потому что возможен перенос исторических проектов |
| `Место` | Необязательно, до 150 символов. Если пусто, не показывать пустую строку в карточке |

Кнопка `Создать свадьбу` доступна после валидного названия. Ошибки показывать рядом с полем и в доступном описании; пустое название — `Укажите название проекта`; превышение длины — `Не более 100 символов`; сетевой сбой — `Не удалось создать свадьбу. Повторите попытку.` Введённые значения при сбое сохраняются. Во время сохранения заблокировать повторный submit, показать состояние загрузки. Закрытие диалога с введёнными данными требует подтверждения только если данные реально изменены.

Сервер создаёт событие в `active` и **один раз** добавляет стартовый план `wedding_v1`. Для первого MVP он состоит из редактируемых задач ниже; все начинают в `planned`, без ответственного и без дедлайна. Сроки нельзя выдумывать по дате свадьбы: относительные сроки и расширенный план будут предметом следующей спецификации. Задача 01 создаётся только если дата пока неизвестна. Это рабочий минимальный шаблон для запуска сценария, а не утверждение о единственно правильном процессе агентства.

| № | Раздел | Стартовая задача |
|---|---|---|
| 01 | Основное | Уточнить дату свадьбы (только если дата неизвестна) |
| 02 | Основное | Заполнить бриф пары |
| 03 | Основное | Согласовать формат и приоритеты свадьбы |
| 04 | Финансы | Определить ориентир бюджета |
| 05 | Площадка | Составить короткий список площадок |
| 06 | Площадка | Подтвердить площадку и договорённости |
| 07 | Подрядчики | Определить необходимые роли подрядчиков |
| 08 | Подрядчики | Согласовать выбранных подрядчиков |
| 09 | Гости | Собрать предварительный список гостей |
| 10 | Логистика | Зафиксировать потребности по размещению и трансферу |
| 11 | День свадьбы | Подготовить черновой тайминг |
| 12 | Финал | Подтвердить финальные договорённости с участниками |

Каждая созданная задача хранит `templateKey` (`wedding_v1:02` и т. д.) и `eventId`; уникальность пары `(eventId, templateKey)` обеспечивает отсутствие дублей. Если в проекте уже есть задачи с этими ключами, повторное создание плана добавляет только недостающие; пользовательские правки существующих задач не перезаписываются. Контракт создания возвращает `eventId` и состояние `planStatus: ready | pending | failed`. При `pending` открыть проект и показать `Создаём план подготовки`; при `failed` проект сохраняется, а в его обзоре показывается действие `Повторить создание плана`. Повтор должен быть идемпотентным.

Для защиты от двойной отправки использовать `idempotencyKey` на запрос создания; сервер проверяет доступ `event:create`. Если шаблон ещё не реализован, не изображать готовый план и не объявлять функцию завершённой при сдаче MVP.

## 6. Поиск, сортировка, архив

- Поиск по `title` и `locationName`, без учёта регистра, нормализовать `ё/е` только если это принято в общей реализации поиска. Пустая строка сбрасывает поиск. Debounce 250–350 мс. При смене вкладки искать внутри выбранной вкладки; поисковый текст сохранять.
- Сортировка `По дате`: проекты с известной датой по возрастанию, без даты в конце, затем `createdAt` по убыванию, затем `id`. Прошедшие активные свадьбы остаются в списке.
- `По вниманию`: сначала большее `urgentCount`, затем дата свадьбы, затем стабильный `id`. Когда у всех `urgentCount = 0`, список практически совпадает с датной сортировкой.
- Архивирование не происходит автоматически после даты свадьбы или после завершения всех задач. Отдельное подтверждаемое действие внутри меню проекта: `Переместить в архив`. На этой странице допустимо меню карточки, если действие уже реализовано. Восстановление — `Вернуть в активные` в архиве.
- Удаление проекта с первого экрана **не включать**. Не показывать неработающую кнопку удаления.
- Пагинация с размером страницы 20, серверная при большом объёме. При изменении поиска/вкладки/сортировки сбрасывать курсор и запрашивать первую страницу.

## 7. Пустые, загрузочные и ошибочные состояния

| Состояние | Что показывает экран | Действие |
|---|---|---|
| Первый вход, нет проектов | `Здесь появятся ваши свадьбы` и одно пояснение: `Создайте первый проект, чтобы собрать подготовку в одном месте.` | `Создать свадьбу` |
| Активных нет, архив есть | `Нет активных свадеб` | `Создать свадьбу` и доступная вкладка архива |
| Архив пуст | `В архиве пока ничего нет` | Вернуться к активным |
| Поиск без результатов | `По запросу «…» ничего не найдено` | `Сбросить поиск`; не предлагать создание как единственный выход |
| Нет срочных пунктов | Блок внимания скрыт; краткая строка `Срочных вопросов сейчас нет` допустима под заголовком списка, если нужна обратная связь | — |
| Загрузка | Скелетоны заголовка блока и 2–3 карточек с фиксированной высотой; `aria-busy` | — |
| Ошибка запроса | `Не удалось загрузить мероприятия` | `Повторить` без потери фильтров |
| Нет прав создать | Кнопка создания скрыта; прямой запрос сервер отвергает | — |

Не показывать настоящее имя другой пары, чужую фотографию или чужой проект в фиктивных skeleton/empty states.

## 8. Адаптивность, доступность и визуальная реализация

Brandbook v1.1 — источник цветов, Involve, сетки, отступов, скруглений, контраста, focus и состояний. **Не перекрашивать экран под коричневый ParaPlanner**. Фото — только загруженные и разрешённые владельцем; если нет фото, использовать нейтральную поверхность/градиент системы без искусственной свадебной фотографии. Стекло допустимо только поверх реального изображения и при проверенном контрасте; на плотном списке непрозрачные карточки.

- Desktop ≥ 1024 px: контейнер до 1440 px; блок внимания во всю ширину или как ясная верхняя зона; карточки в две колонки при достаточной ширине. Заголовки и действия не разносить так далеко, чтобы кнопка создания терялась.
- Tablet 768–1023 px: одна/две колонки по фактической ширине карточки не менее 320 px; элементы фильтра могут переноситься строкой.
- Mobile < 768 px: одна колонка; заголовок и кнопка создания на отдельных строках при необходимости; поиск во всю ширину; вкладки видимы целиком; сортировку открыть в компактном меню. Карточка не должна иметь горизонтального скролла, длинное название переносится до двух строк, полное доступно внутри проекта.
- Минимальный интерактивный размер 44×44 px; видимый фокус; `button` для действий, `a` для переходов; вкладки с семантикой tabs или обычные ссылки с обозначением активной; метки ошибок и срочности словами, не одним цветом. Клавиатура: открыть/закрыть диалог, Escape, возврат фокуса на кнопку создания. При смене фильтра объявлять число результатов в `aria-live=polite` без спама на каждый символ.
- Числа, время и дата локализованы на русском. Полная дата и часовой пояс доступны в `title`/accessible label у относительных формулировок. Не писать `до свадьбы −3 дня`.

Не подменять фирменный шрифт временным шрифтом, если файлы Involve предоставлены. Если файлов нет, используйте предусмотренный в брендбуке fallback и пометьте отсутствующие ассеты в handoff; не скачивайте случайную версию с внешнего сайта.

## 9. Крайние случаи и безопасность

1. Два проекта с одинаковым названием допустимы — различаются по `id`, дате и/или месту. Не использовать title в URL или как ключ списка.
2. Очень длинные названия/места не ломают карточку. Пустые и пробельные названия отвергаются сервером. Выводимый текст экранируется, HTML из ввода не исполняется.
3. Переход из общего блока внимания к проекту без доступа возвращает корректный 403/404 без раскрытия данных. Удалённая/закрытая задача при клике открывает обзор с сообщением `Элемент больше недоступен`, а не пустой экран.
4. Если дата изменена, карточка пересортировывается; список не должен перескакивать во время ввода в другом окне. Обновлять при возврате фокуса.
5. При отсутствии сети после первоначальной загрузки можно показывать последнюю уже загруженную страницу с явным `Нет соединения`; действия записи блокируются/ошибка сообщается, ложного подтверждения нет.
6. Прямое открытие архивного проекта допустимо пользователю с доступом; архив — состояние проекта, а не способ скрыть его от поиска по прямой ссылке.
7. Рабочее пространство с 50 проектами должно оставаться пригодным: серверные поиск/сортировка/пагинация, запросы без N+1 на агрегаты задач.

## 10. Технический контракт и порядок сборки

Стек неизвестен: Claude Code сначала проверяет существующие роутер, auth, модели, API, компоненты и токены. Повторно не создаёт их. Если репозитория ещё нет, экран можно собрать на моках **только для визуальной проверки**, при этом API слой и демонстрационные данные отделить от UI; нельзя выдавать моки за работающий продукт.

Минимальные операции сервера (адаптировать к принятым в проекте API conventions):

```text
GET  /events?lifecycle=active|archived&q=&sort=date|attention&cursor=&limit=20
GET  /events/attention?cursor=&limit=20  // только если внимание загружается отдельно
POST /events  { title, eventDate|null, locationName|null, idempotencyKey }
POST /events/:id/archive          // если действие включено в сборку
POST /events/:id/restore          // если действие включено в сборку
```

Рекомендуемый вариант — `GET /events` вместе с `attentionPreview` и `attentionTotal` для согласованности и уменьшения сетевых запросов. Отдельный `GET /events/attention` нужен только для догрузки после первых пяти. Установить предел на строковые поля также на сервере. Доступ к `GET` и `POST` проверяется на сервере по рабочему пространству и разрешениям.

Реализация по шагам: (1) route/auth → (2) серверный список + точные агрегаты → (3) карточка/фильтры/состояния → (4) создание → (5) мобильный layout → (6) проверка доступности и сценариев. Сначала сделать реальные данные и правила, затем добавить визуальные эффекты по брендбуку.

## 11. Критерии приёмки

Экран считается готовым, когда на тестовых данных можно воспроизвести все пункты ниже:

1. Организатор с тремя активными свадьбами и одной архивной видит верные счётчики; архив не смешивается с активными.
2. Просроченная задача и заблокированная задача из разных свадеб появляются в общем блоке; каждая карточка показывает своё точное `urgentCount`; завершённая задача исчезает после обновления.
3. Задача со сроком сегодня отображается `Сегодня`; после наступления времени срока — `Просрочено`. Date-only срок остаётся «Сегодня» весь день и становится просроченным на следующий день в часовом поясе пространства.
4. Задача `waiting` без наступившего `followUpAt` не попадает в срочные. При наступлении даты попадает как `Нужно напомнить`.
5. Две разные свадьбы с одним названием открываются по разным `id`.
6. Поиск находит проект за пределами первых 20 карточек; сортировка и вкладка работают над всем набором, а URL сохраняет состояние.
7. Создание с названием и неизвестной датой работает; без названия показывает ошибку; повторный клик/повтор запроса с тем же ключом не создаёт дубликат.
8. Сбой создания плана не стирает созданный проект и не создаёт дубли задач при повторе.
9. Пользователь без доступа не видит чужой проект в списке и не может получить его через прямой API запрос.
10. Экран пригоден на ширине 375 px и 1440 px, без горизонтальной прокрутки; клавиатура и screen reader достигают всех действий; видимый фокус и контраст соответствуют брендбуку.
11. В интерфейсе нет демонстрационных KPI, неработающих кнопок, чужих стоковых фото или статусов, которые противоречат дедлайнам.
