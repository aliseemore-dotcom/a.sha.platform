# Обзор мероприятия — единое ТЗ v2 для Claude Code

**Экран:** обзор конкретного проекта после перехода из «Мои мероприятия».  
**Контекст:** текущие desktop/mobile макеты «Мария + Илья», брендбук Soft Editorial Glass, единое ТЗ страницы «Мои мероприятия».  
**Цель:** за короткое время показать организатору, что требует внимания, что выполняется и где ожидается ответ; дать переход к конкретному действию. Этот документ заменяет прежнюю версию ТЗ обзора целиком.

## 0. Область работ и ключевое решение

Доработать существующий экран проекта, сохранив его данные и работающие переходы. Обзор **не должен показывать одни и те же задачи четыре раза**. Оставить шапку, три ориентирующих показателя и три рабочих блока: «Требует внимания», «В работе», «Ждём ответа». Внизу — одна ссылка «Открыть все задачи», ведущая к полному рабочему списку. Удалить с обзора отдельные блоки «Ближайшие задачи» и «Все задачи» с повторными строками. Если полноценного маршрута задач ещё нет, реализовать его как простой отдельный вид проекта (список существующих задач), либо оставить ссылку на уже работающий список; не вести в пустой placeholder.

В каждом из трёх рабочих блоков задача **визуально показывается один раз на странице**, хотя её свойства могут относиться к нескольким показателям. Правило размещения: «Требует внимания» имеет приоритет над «Ждём ответа», затем над «В работе». Например, просроченная задача со статусом `in_progress` находится в первом блоке и получает дополнительный маленький бейдж «В работе». Если ждём флориста и истёк дедлайн самой задачи, задача находится в первом блоке с пометкой «Ждём: флорист». В нижних блоках она второй строкой не повторяется.

Числа трёх показателей означают **полные размеры соответствующих множеств**, поэтому они могут пересекаться и не складываются. Если «В работе · 2», но одна задача уже показана выше как срочная, в блоке остаётся одна строка и ясная ссылка «Ещё 1 задача показана в „Требует внимания“». Клик по ней прокручивает и выделяет нужную строку сверху. Аналогично для ожидания. Нельзя показывать заголовок «В работе · 2» над одной строкой без объяснения.

## 1. Данные и правила

### 1.1 Проект

Использовать существующий проект: `id`, `title`, `eventType`, `eventDate` (nullable), `venue` (nullable), `lifecycleStatus`, `coverImage` (optional), доступы участников. Прошедшая дата не архивирует проект автоматически. Активный проект с будущей датой — «В подготовке», после даты — «Завершение проекта»; архивный — «В архиве». Два проекта с одинаковым названием различать по ID.

### 1.2 Задача и статусы

Опорные поля: `id`, `projectId`, `title`, `status` (`todo`/`in_progress`/`waiting`/`done`/`cancelled` или существующие эквиваленты), `dueAt` (nullable), `assigneeId` (nullable), `blocked` и `blockedReason` (если поддержаны), `waitingFor` (структурированное лицо/роль, если поддержано), `followUpAt` (контрольный срок, если поддержан). Не выводить эти состояния из слов в названии. Завершённые и отменённые не входят в три рабочих показателя.

**Срок выполнения (`dueAt`)** — когда должна быть выполнена задача. Именно он создаёт метки «Сегодня» и «Просрочено». **Контроль ожидания (`followUpAt`)** — когда организатор планирует проверить ответ или напомнить другой стороне. Это отдельная дата: она не заменяет дедлайн задачи и не должна отображаться как «задача просрочена». Пока нет явных полей и действия «Напомнили / перенести контроль», показывать контрольную дату лишь как информацию, не создавать автоматически тревожный сигнал «Нужно напомнить». Если в текущем прототипе «Просрочено с 15:16» получено из контрольной даты ожидания, исправить это смешение: статус ожидания остаётся «Ждём ответа», а контроль показывается отдельно.

**Внимание** — незавершённая задача, у которой есть явная блокировка, или срок выполнения уже прошёл, или срок выполнения сегодня. Использовать ту же функцию и часовой пояс, что на странице «Мои мероприятия». Если задача и заблокирована, и просрочена, считать один объект. Срок завтра не просрочен; дата без времени истекает в конце локального дня агентства, показывается без придуманного часа. Метки обновляются на границе времени и при возвращении на вкладку. Не превращать `waiting` автоматически в «Заблокировано».

**В работе** — задачи с подтверждённым статусом `in_progress`. **Ждём ответа** — задачи с подтверждённым статусом `waiting`. Одна задача обычно имеет один рабочий статус, но может параллельно иметь признак срочности. Если существующая схема не позволяет выразить эти состояния, зафиксировать недостающие поля перед реализацией вместо имитации.

### 1.3 Пример, который должен работать

При данных из текущего макета: «Отправить подрядчикам финальный тайминг» = `in_progress` + просроченный `dueAt`; «Утвердить декор зала» = blocked; «Согласовать смету с флористом» = `waiting` + просроченный `dueAt`; «Рассадка гостей» = `in_progress` без срочности.

Показатели: «Требует внимания 3», «В работе 2», «Ждём ответа 1». Верхний блок показывает первые три задачи, с маленькими вторичными признаками их рабочих состояний. Ниже в «В работе» показывается только «Рассадка гостей» и пояснение со ссылкой, что ещё одна задача находится выше. «Ждём ответа» показывает пояснение/ссылку на задачу флориста выше; если нет несрочных ожидающих задач, не оставлять огромную пустую карточку. Каждая из четырёх активных задач имеет **одну видимую основную строку на обзоре**. Готовая задача «Подтвердить трансфер гостей» доступна в полном списке, а не на обзоре.

## 2. Экран и действия

### 2.1 Навигация и шапка

«← Мои мероприятия» возвращает к списку, сохраняя вкладку/поиск при обычном возвращении, если архитектура приложения позволяет. При прямом входе ведёт к стандартному списку. Показать тип события, название, статус, дату и площадку только при наличии данных. При отсутствии даты — «Дата уточняется»; при отсутствии площадки строку скрыть. «Через N дней» только для будущей даты, в день события — «Сегодня»; отрицательное значение не показывать. Длинные названия и площадки переносятся.

Редактирование данных проекта и архивацию поместить в доступное меню `⋮` с читаемой меткой для клавиатуры и скринридера. Действие архивации доступно лишь роли с правом и сопровождается подтверждением и понятным способом восстановить проект. Не выносить его как главную кнопку обзора. Фото показывать только при реальной обложке, без случайного стока.

### 2.2 Три показателя

Показывать «Требует внимания N», «В работе N», «Ждём ответа N» в этом порядке. Каждый показатель интерактивен: ведёт к соответствующему блоку; если все задачи выбранной группы показаны в верхнем блоке, прокручивает к первой из них и показывает подсказку о пересечении. Показатели строятся из данных, не хардкодятся как 3/2/1. На mobile подписи переносятся без обрезания и все три карточки сохраняют читаемость; при тесной ширине допустим двухрядный layout.

### 2.3 Требует внимания

Первый рабочий блок. Заголовок **«Требует внимания · N»**, потому что «отправить тайминг» — действие, а не управленческое решение. До пяти строк на desktop и до трёх на mobile, затем «Показать все N»/«Свернуть» (если элементов больше лимита). Сортировать по правилам главной: блокировка/просрочка/срок сегодня с устойчивым вторичным порядком; никакой дубликации одной задачи внутри блока.

В строке: компактный бейдж причины («Заблокировано», «Просрочено 2 дня», «Сегодня 19:42»), название, ответственный, срок при наличии. Если задача также `in_progress` или `waiting`, можно показать небольшой вторичный признак, чтобы повторять её в нижних блоках не понадобилось. Не повторять в каждой строке название пары — пользователь уже находится в проекте. Клик ведёт к конкретной задаче. При отсутствии срочного — компактный текст «Сейчас нет задач, требующих срочного действия».

### 2.4 В работе

Показать только `in_progress` задачи, **не показанные выше**, с ответственным и сроком, если есть. Сортировка по ближайшему сроку, затем стабильно по ID. Если часть задач уже в верхнем блоке, пояснить расхождение счётчика и строк ссылкой «Ещё N задач(и) показаны выше». Если все задачи в работе показаны выше, компактное пояснение заменяет пустую карточку. Если таких задач вообще нет — «Пока нет задач в работе». Не подменять их задачами `todo`.

### 2.5 Ждём ответа

Показать только `waiting` задачи, **не показанные выше**. При наличии структурированных данных указывать, от кого ждём, ответственного внутри команды и контрольную дату; при отсутствии адресата — просто «Ждём ответа» и название задачи. Если ожидающая задача уже в верхнем блоке, вместо второй строки дать ссылку «N ожидающих задач показаны выше». При отсутствии ожидающих — краткое пустое состояние или скрытие блока; не оставлять равновысокую пустую карточку.

Контрольная дата не тождественна сроку выполнения. До внедрения действия «Напомнить», истории контакта и переноса контрольной даты это информационный атрибут. Не отправлять сообщений автоматически.

### 2.6 Переход ко всем задачам

В конце обзора одна хорошо заметная ссылка **«Открыть все задачи →»** и, если разрешено пользователю, действие **«+ Добавить задачу»**. Полный список содержит `todo`, `in_progress`, `waiting`, `done` и фильтры/сортировки согласно отдельному ТЗ модуля задач. В рамках этого задания не строить второй полный список внутри обзора. Если рабочий список уже существует — использовать его маршрут; если пока отсутствует, сделать минимальный маршрут со списком существующих задач и открытием записи, без фиктивных функций.

## 3. Карточка задачи и синхронизация

Клик из любой строки или с глобальной главной открывает одну и ту же задачу по устойчивому URL с `projectId`/`taskId` (либо уже принятому эквиваленту); обновление и новая вкладка сохраняют контекст. На mobile допустима полноэкранная панель, на desktop — боковая. Показывать статус, ответственного, **срок выполнения** и отдельно **контроль ожидания**, если заполнен. Кнопка выхода — «Вернуться к проекту»/«Закрыть карточку»; «Закрыть задачу» не использовать для закрытия панели. «Отметить выполненной» сохраняет изменение; при ошибке показывает ошибку и возможность повтора. После сохранения все три счётчика, строки обзора и счётчик главной обновляются из единого источника.

Если задача удалена/недоступна, показать понятное сообщение и ссылку к проекту, не подставлять другую задачу. Доступ к проекту/задаче проверяется на сервере. Архивные проекты исключаются из глобальной срочности; внутри архива обзор можно показывать как историю согласно действующей модели прав.

## 4. Адаптив, визуал, состояния

Desktop: после шапки показатели и блок внимания на ширину рабочей области; «В работе» и «Ждём ответа» могут быть рядом, если текст и ссылки не сдавлены. Mobile: одна колонка — шапка → показатели → внимание → в работе → ожидание → переход ко всем задачам. Не добавлять громоздкие вложенные рамки. Бейджи компактны, границы тонкие, цвета и типографика из брендбука и принятой дизайн-итерации главной. Строки доступны с клавиатуры и имеют видимый фокус; интерактивные области на mobile не менее 44×44 CSS px. Статус выражен текстом, а не только цветом.

Новый проект без задач: шапка и краткое начальное состояние с рабочим действием «Добавить первую задачу» вместо трёх больших пустых блоков. Нет внимания, но есть работа/ожидание: спокойное компактное состояние первого блока. Нет даты/места/ответственного: соответствующие подписи, без `undefined`. Загрузка: скелетоны, без ложных нулей. Ошибка: сообщение и «Повторить». Нет доступа/проект удалён: безопасный возврат к списку.

## 5. Критерии приёмки

1. На мобильном после трёх рабочих блоков есть только ссылка ко всем задачам; «Ближайшие задачи» и повторная таблица «Все задачи» отсутствуют.
2. Ни один `taskId` не имеет более одной основной строки на обзоре. Срочная задача `in_progress` стоит в «Требует внимания», а блок «В работе» объясняет, почему строк меньше, чем показывает счётчик.
3. Заголовок первого блока «Требует внимания»; задача «Отправить тайминг» не обозначается как «решение».
4. `dueAt` и `followUpAt` отображаются и рассчитываются отдельно. Просрочка срока задачи не вычисляется из контрольной даты ожидания; «Нужно напомнить» не появляется без явного сценария.
5. Три числа отражают полные группы, могут пересекаться, интерактивны и пересчитываются после завершения/изменения задачи. Одна задача в группе внимания считается там один раз.
6. Прямой URL открывает нужную задачу, в карточке видны обе даты при наличии, возврат и завершение различимы.
7. Проект после даты события остаётся активным до архивации, статус «Завершение проекта»; архивация в меню и зависит от прав.
8. Проверить desktop/mobile на насыщенном проекте из примера, пустом проекте, проекте без срочного и проекте с длинными именами. Ничто не уходит за экран и нет ложных данных при загрузке.

## 6. Проверка совместимости с существующим кодом

Перед изменениями Claude Code должен найти существующие модель задачи, вычислитель срочности, маршруты, компоненты статусов и права доступа. Переиспользовать их. Если отсутствуют `blocked`, `waiting`, `waitingFor` или `followUpAt`, перечислить конкретные пробелы и предложить минимальный контракт/миграцию; не угадывать состояние по тексту. Не реализовывать отправку напоминаний или клиентское согласование в рамках этой страницы. Отдельное ТЗ для полного модуля задач будет следующим этапом.
