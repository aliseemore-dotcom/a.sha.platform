## Обзор мероприятия v2 (specs/02-overview-v2.md) — ключевое решение и находки

**Ключевое решение — дедупликация.** Каждая задача показывается на странице ровно один раз.
Приоритет размещения: «Требует внимания» → «Ждём ответа» → «В работе» (§0). Задача, которая
одновременно просрочена/заблокирована и находится в работе или в ожидании, получает маленький
второй бейдж прямо в строке «Требует внимания» (`В работе` или `Ждём: <источник>`) и не повторяется
строкой в блоке ниже. Три числа сверху — это **полные размеры** множеств (могут пересекаться), а
не число видимых строк; когда часть задач блока уже показана выше, вместо пустой/усечённой карточки
блок показывает «Ещё N задач(и) — в «Требует внимания» выше» со ссылкой, которая **прокручивает и
подсвечивает** конкретную скрытую строку.

**Блоки «Ближайшие задачи» и «Все задачи» на обзоре убраны** (§0: «не показывать одни и те же
задачи четыре раза»). Вместо них — одна ссылка «Открыть все задачи →», ведущая на новый минимальный
маршрут `/events/:id/tasks` (`web/js/views/taskList.js`) со сгруппированным по разделам списком всех
задач, включая завершённые/отменённые (единственное место в проекте, где они видны).

**Находка при проверке в браузере — `:target` не работает в этом стеке.** Изначально подсветку
скрытой строки планировалось делать нативной ссылкой на `#якорь` + CSS `:target`. Эмпирически
выяснилось: для ЛЮБОГО элемента внутри корневого узла приложения (`#root`, куда монтируется вся
SPA) браузер не проставляет `:target` даже при абсолютно корректном `location.hash` и полном
совпадении `id` — при этом тот же CSS `:target` исправно работает для элементов вне этого узла.
Причина осталась не до конца ясна (не нашлось связи с `aria-busy`, `overflow`, `id="root"` как
строкой, тегом `<main>` — переименование/замена узла не помогает), поэтому «прокрутка и подсветка»
переписана на обычный JS (`scrollIntoView` + временный класс + перевод фокуса) — надёжнее, работает
одинаково для одной строки и для целого раздела, и заодно двигает фокус клавиатуры/скринридера, чего
`:target` не делает. Заодно тем же попутно чинили общий баг: глобальный перехватчик кликов в
`app.js` вызывал `preventDefault()` для абсолютно любой ссылки на этой же странице, включая обычные
`#якорь`, и то же самое `pathname+search` не менялось — то есть **любая** ссылка на внутристраничный
якорь до этого молча ничего не делала (см. «Мимоходом» в истории коммитов).

**Недостающее поле, которое пришлось добавить:** `waitingFrom` (кого/что ждём — площадку,
подрядчика, пару) на задаче. Без него строка «Ждём ответа» не могла бы показывать «от кого» (§1.2,
`waitingFor`). Добавлено как обычное необязательное поле задачи, попадает в контракт `GET /api/events/:id`.

**Поле, которое сознательно не стали вводить:** момент, с которого длится ожидание — отдельно от
контрольной даты `followUpAt` (§1.2 явно требует не путать их). У задачи есть только `updatedAt`
(общая метка последнего изменения) — использовать её значило бы угадывать: `updatedAt` меняется по
любой причине, не только при переходе в `waiting`. Если понадобится честное «с какого момента» —
нужно отдельное поле, проставляемое в момент перехода в `waiting`.

**Не реализовано умышленно, а не забыто** (§6: «перечислить пробелы, не угадывать»):
- *Редактирование базовых данных проекта* — в спецификации упомянуто как пункт меню, но её
  собственное поведение (поля, валидация, права) нигде не описано; показывать пункт меню, который
  ничего не делает, сама спецификация запрещает, поэтому в меню — только архив/восстановление.
- *«+ Добавить задачу»* (§2.6) — доступно «только там, где реально реализовано»; создания
  произвольных задач в API нет (есть только стартовый план и отметка «выполнено»).
- *Фото обложки* — путь отрисовки поддержан (`event.coverUrl` → `<img class="overview-cover">`),
  но в демо-данных фото нет ни у одного проекта: подставлять сток брендбук прямо запрещает.

**Решения там, где документ оставляет выбор:**

| Пункт | Как сделано |
|---|---|
| Общие компоненты и функция срочности с «Мои мероприятия» | Строка задачи — общий `taskRow()`; «Требует внимания» использует ту же функцию (`buildAttention`/`classifyTask`) через `GET /api/events/:id`, поэтому число здесь и на списке никогда не расходится |
| «До пяти на desktop и до трёх на mobile» | Тот же лимит, что на «Мои мероприятия»: `web/js/breakpoints.js`, общий модуль |
| Раскрытие «Требует внимания» | Список одного проекта обычно небольшой, поэтому «Показать все N» разворачивает уже загруженные данные на клиенте — без отдельной пагинации, в отличие от глобального списка |
| «В работе» / «Ждём ответа» | Полный список `in_progress` / `waiting`, не показанных выше, без верхнего предела на количество — рабочий, а не декоративный блок |
| Сортировка «В работе» | Ближайший срок → стабильно по `id` (§2.4: «затем стабильно по ID») |
| Сохранение состояния списка при возврате | Ссылки на карточки и на глобальные строки внимания несут `?from=<путь списка>`; «← Мои мероприятия» использует его, если он указывает на `/events…`, иначе — обычный список |
| Показатель без собственных строк (§2.2) | Клик по «В работе»/«Ждём ответа», когда все задачи группы уже показаны выше, прокручивает и подсвечивает первую из них, а не сам (пустой) блок |

## Сделано

- Маршруты `/events`, `/events/:id/overview`, `/events/:id/tasks/:taskId`, `/events/:id/tasks`
  (полный список); без сессии — переход на вход с безопасным `returnTo`.
- Серверный список: вкладки с счётчиками до поиска, поиск по названию и месту (регистр, ё/е),
  сортировки «По дате» и «По вниманию», пагинация по 20 курсором.
- «Требует внимания»: `blocked → overdue → due_today`, один объект — один раз;
  сроки с точностью `dueAt` (со временем) или `dueDate` (день; просрочен со следующего дня в поясе пространства).
  5 строк на компьютере / 3 на телефоне, «Показать все N» раскрывает.
- Карточка: дата или «Дата уточняется», место, состояние, один срочный повод, до двух «В работе»,
  «Открыть проект»; «Дата прошла · проект активен» без отрицательного отсчёта.
- Обзор проекта: шапка со стадией и «через N дней», три показателя-перехода, «Требует внимания»,
  «В работе», «Ждём ответа» — без повторов задач между блоками, с указателем на скрытую строку
  выше, ссылка «Открыть все задачи →» на отдельный полный список, меню архивирования, панель
  одной задачи с «Отметить выполненной».
- Создание: диалог с проверкой полей, `idempotencyKey`, стартовый план `wedding_v1`
  с уникальностью `(eventId, templateKey)`, `planStatus` и «Повторить создание плана».
- Архив и возврат из архива (owner). Удаления нет.
- Состояния: скелетоны, ошибки с «Повторить», пустые состояния, «Нет соединения».
- Автообновление: при возврате фокуса, по таймеру `refreshAt`, после создания/восстановления/выполнения задачи.
- Шрифт Involve (8 начертаний, woff2, `font-display: swap`) и лицензия OFL — `web/fonts/`.
- Проверено в Chromium на 375 и 1440 px без горизонтальной прокрутки, включая длинные названия и площадки.

## «Задачи мероприятия» (docs/specs/03-tasks.md) — решения и отступления

| Пункт | Как сделано |
|---|---|
| Статус и блокировка | `status` (`todo`/`in_progress`/`waiting`/`done`/`cancelled`) и `isBlocked`/`blockedReason` — независимые поля. `planned` переименован в `todo`; `blocked` как значение `status` удалён — заблокированной может быть задача в любом рабочем статусе (`server/tasks.js`, `server/attention.js`) |
| Расширение модели | Добавлены `description`, `isBlocked`, `blockedReason`, `waitingFrom` (текстовое поле — общей базы подрядчиков нет), `followUpAt`, `completedAt`, `completedBy`, `previousStatus` — `blankTaskFields()` в `server/tasks.js`, используется и созданием задачи, и стартовым планом (`server/plan.js`) |
| Восстановление после `done` | Возвращает `previousStatus`, если он сохранён (записывается при переходе в `done`), иначе `todo` — новой активной записи не создаётся, правится та же задача |
| Список: сортировка «Внимание» | Заблокированные и просроченные — одна группа по давности срока, затем «Сегодня», затем по `dueAt`, без срока — в конце; вторичный ключ `createdAt`, затем `id` (`byAttentionThenDue` в `server/tasks.js`) — общая функция с «Мои мероприятия»/обзором через `classifyTask` |
| Вкладки | «Открытые» (`todo`/`in_progress`/`waiting`), «Завершённые» (`done`), «Отменённые» (`cancelled`) — реализованы как три вкладки с отдельными счётчиками, а не «фильтр поверх завершённых», как буквально описано в ТЗ; отменённые ни при каких обстоятельствах не смешиваются с выполненными |
| «Проверить ответ» | Фильтр `waiting` + `followUpAt <= сегодня`; не считается во «Требует внимания» ни на одном экране — сознательно, по ТЗ (раздел 0) |
| Двойное нажатие «Сохранить» | `idempotencyKey` на создание задачи (как у создания мероприятия), повтор с тем же ключом возвращает ту же запись, а не дубль |
| Конкурентное изменение | `expectedUpdatedAt` в теле правки; расхождение с текущим `updatedAt` — `409 conflict`, запись не перезаписывается молча |
| Карточка задачи | Отдельный маршрут `/events/:id/tasks/:taskId` (`web/js/views/taskDetail.js`), не встроена в обзор — работает после перезагрузки и в новой вкладке. Кнопка возврата подписана по контексту входа (`from` в URL): «Вернуться к задачам» из списка, «Вернуться к проекту» из обзора и при прямом переходе |
| Обзор проекта | Панель одиночной задачи, встроенная в обзор (Фаза 8), убрана — обзор ссылается на карточку задачи тем же маршрутом, что и список |
| Архив | Список задач архивного проекта доступен для чтения; создание/редактирование/переходы статуса запрещены на сервере (`409 archived`), кнопка «Добавить задачу» скрыта в интерфейсе |

Не включено по разделу 0 ТЗ (сознательно, чтобы не создавать нерабочих кнопок): шаблоны свадебных
планов сверх черновой панели выбора (см. раздел ниже — она заменила прежний автоматический
стартовый план), вложенные подзадачи, комментарии, вложения, интеграция с мессенджерами,
автоматическая отправка сообщений и согласования с клиентом.

### Известная ловушка вёрстки

`[hidden]` проигрывает `display`, заданный классом той же специфичности (`.btn[hidden]`,
`.field-row[hidden]` и т.п. — атрибутный селектор UA-таблицы стилей той же специфичности, что
и классовый, но автор объявлен позже). Исправлено одним общим правилом в начале `app.css`:
`[hidden] { display: none !important; }`. При добавлении новых элементов с явным `display` в
классе и последующим переключением `hidden` из JS отдельная переопределяющая строка на класс
больше не нужна.

| Пункт | Как сделано |
|---|---|
| Модель | `server/budget.js` + `server/store.js` (`budgets`, `budgetLines`): смета — отдельный объект на проект (`{ eventId, currency }`), строки хранятся отдельно от подрядчиков и задач. Расширил личную базу подрядчиков (`server/vendors.js`) полями `price`/`currency` — их не было до этого ТЗ |

| Валюта: без молчаливой конвертации | При создании строки: если `vendor.currency !== budget.currency`, `amount: null` независимо от того, есть ли цена; `originalPrice`/`originalCurrency` сохраняются для показа исходного значения (`needsCurrencyMatch` в ответе). Сумму в валюте сметы организатор вводит вручную через тот же `updateBudgetLine` |
| Итог и «не хватает цены» | `getBudget` считает `total` и `missingCount` из **включённых** строк за один проход при каждом чтении — не кешируется и не хранится отдельно, значит не может разойтись со списком строк |
| Удаление подрядчика: две судьбы строки | `removeEventVendor(ctx, eventId, linkId, budgetAction)` — `'delete'` удаляет строку вместе с подрядчиком, `'keep'` (`resolveVendorLine`) отвязывает её (`source: 'manual'`, `sourceEventVendorId: null`), сумма и `included` остаются как были. ### Известная ловушка (снова та же, не в первый раз)

Нативный `Element.append(...)` превращает `null` в текстовый узел `"null"`, если передать его аргументом напрямую (а не отфильтровать). Наступил на неё в `budget.js` при первой реализации (`renderTotal`, финальный `main.append`) — исправлено через `.append(...[…].filter(Boolean))`, как уже сделано в `overview.js`. При добавлении новых экранов с условными дочерними узлами — фильтровать `null` явно перед `.append(...)`, `h()` сам по себе это уже делает, а нативный `append` — нет.
   эти пункты в меню и в «Все задачи» по-настоящему, а не заглушками.

## Фундамент для пилота (docs/specs/08-foundation.md) — решения и отступления

| Пункт | Как сделано |
|---|---|
| `node:sqlite` доступен без флага | Проверено на установленном Node 22.22.2 (`engines.node` поднят до `>=22.13.0`): `DatabaseSync` работает без `--experimental-sqlite`. Node сам печатает в stderr одноразовое `ExperimentalWarning: SQLite is an experimental feature and might change at any time` при первом обращении к модулю — это не блокирует запуск и не мешает работе, только информирует; специально не подавлялось (`NODE_NO_WARNINGS` и т. п.), чтобы это предупреждение оставалось на виду у того, кто эксплуатирует сервис, до тех пор пока API не станет стабильным в самом Node |
| Два хранилища, один интерфейс | `server/store/memory.js` (бывший `server/store.js`, поведение не менялось) и `server/store/sqlite.js` (`DatabaseSync`, `journal_mode=WAL`, `foreign_keys=ON`, `busy_timeout=5000`). `server/store.js` — точка выбора, `createStore` (имя для обратной совместимости с тестами) = память, `createSqliteStore` = SQLite. `test/store.contract.test.js` — 26 тестов на обеих реализациях одним и тем же кодом |
| Копии, а не живые объекты | Обе реализации прогоняют объекты через `structuredClone` на входе и выходе — правка возвращённого объекта снаружи не меняет сохранённые данные ни в памяти, ни в SQLite (проверено контрактным тестом) |
| `memberIds` — отдельная таблица | И в памяти (`Map<eventId, Set<userId>>`), и в SQLite (`event_members`) — `insertEvent`/`updateEvent` сами извлекают `memberIds` из объекта и пишут в свою структуру, `getEvent` собирает их обратно. `access.js` и весь остальной код продолжают читать `event.memberIds` как раньше |
| Транзакции: где обёрнуто, а где сознательно нет | `createEvent` — вставка события и запись ключа идемпотентности вместе; `addChecklistItems`, `rescheduleTasks`, `addEventVendors` (с созданием строк сметы), `removeEventVendor` (с судьбой строки сметы) — весь цикл вставок/правок в одной транзакции. **Отступление от буквы §1.4**: применение стартового плана внутри `createEvent`/`retryPlan` (`runPlan` в `server/events.js`) НЕ обёрнуто в общую транзакцию с созданием события. Причина: уже существующий и обязательный к сохранению тест «сбой плана не удаляет проект» (`test/events.test.js`) проверяет именно частичное применение — задачи, вставленные до сбоя, остаются, `planStatus` становится `failed`, а «Повторить создание плана» достраивает недостающее по тому же принципу идемпотентности `templateKey`. Откат всего плана целиком стёр бы это уже протестированное и полезное поведение (пилотный организатор не должен терять уже созданные 5 из 13 задач только из-за сбоя на 6-й). Раздел 0 ТЗ 08 требует не ломать существующие тесты — это имеет приоритет перед буквальной формулировкой §1.4 |
| Схема | `server/db/migrations/001_init.sql` — все таблицы из §1.5. Почти все поля сущности хранятся целиком в `data` (JSON), а не только «остальные, не попавшие в отдельные столбцы»: отдельные столбцы дублируют id/связи/уникальность только для индексов и `WHERE`, но не вычитаются из `data` при записи — так проще и безопаснее (нет риска расхождения между «столбцом» и «остатком JSON» при добавлении новых сервисных полей), а по объёму данных пилота (десятки свадеб) это не имеет значения |
| Миграции | `server/db/migrate.js` — каждый файл в своей транзакции, применённые — в `schema_migrations`; повторный старт не переприменяет и не падает (`test/migrations.test.js`, включая настоящий файл на диске, не только `:memory:`) |
| Пароли | `crypto.scryptSync`, N=2¹⁵/r=8/p=1, соль 16 байт, параметры хранятся в самой строке хэша (`scrypt$N$r$p$saltHex$hashHex`) — можно поднять позже без миграции старых записей. Сравнение — `timingSafeEqual` |
| Сессии | Cookie хранит только случайный токен (32 байта, base64url); в базе — только SHA-256 от него (`sessions.idHash`). 30 дней, продление `lastSeenAt`/`expiresAt` не чаще раза в час. `Secure` — только при `DEMO=0` |
| Вход и ограничение попыток | Один и тот же текст ошибки на неверный email и неверный пароль. 5 попыток на пару email+IP за 15 минут, 30 на IP — оба порога проверяются независимо (`server/auth/loginAttempts.js`) |
| Приглашения и сброс пароля | Общая таблица `invites` с `kind: 'invite' | 'reset'`. Токен в базе не хранится, как у сессий. Новое приглашение на тот же email заменяет активное (`findActiveInviteByEmail` + `invalidateInvite`). Email, уже занятый другим пользователем на принятии приглашения, — та же общая ошибка «Ссылка недействительна», без уточнения, что не так — специально, чтобы не подтверждать существование чужого аккаунта |
| Владелец создаётся только через приглашение | `create-workspace` не задаёт пароль сам — печатает ссылку с `kind: 'invite'`, `role: 'owner'`; владелец проходит тот же путь `/invite/:token`, что и обычный участник. Значит для владельца не нужен отдельный код создания пользователя — на 100% переиспользуется `acceptInvite` |
| Участники свадьбы | Диалог «Участники» показывает только пользователей с ролью `member`, которые **уже приняли приглашение** (существуют как записи `users`) — если пригласить кого-то и сразу попытаться добавить в свадьбу до того, как он перешёл по ссылке, его не будет в списке кандидатов. Это соответствует тексту ТЗ («список пользователей пространства с ролью member»), но стоит иметь в виду при обучении организаторов: сначала пусть коллега примет приглашение, потом добавляйте его в свадьбу |
| `resolveTimeZone` при `DEMO=0` | Только `workspace.timeZone`; заголовок `X-Time-Zone` от клиента больше не читается веткой `DEMO=0` вообще (клиент может продолжать его слать — просто не используется). Так как `workspace.timeZone` обязателен с момента создания пространства (`create-workspace` требует `--time-zone`), запасного значения `UTC` в проде на практике не должно понадобиться — оно в коде только как защита от пустой строки в базе |
| Часовой пояс: «Время в пространстве» в шапке | Показывается как `Время в пространстве: Europe/Moscow, 14:05` (сырой IANA-идентификатор + время), а не «Москва, 14:05», как в примере ТЗ. Перевод произвольного IANA-имени в русское название города потребовал бы отдельного словаря на несколько сотен зон без явной пользы для пилота на 2–3 организатора — решение зафиксировано здесь, а не реализовано обходным путём (жёстко зашитый словарь на десяток популярных городов создал бы иллюзию полноты и странно вёл бы себя на всех остальных поясах) |
| «Скачать данные пространства» | `GET /api/workspace/export`, только владелец — единый JSON: пространство, пользователи (без `passwordHash`), свадьбы, задачи, личные базы подрядчиков всех пользователей пространства, подрядчики свадеб, сметы и их строки. Отдаётся как `Content-Disposition: attachment`, скачивается обычной ссылкой `<a href>`, без отдельного JS-кода на клиенте |
| Резервные копии | `VACUUM INTO` ежедневно в 03:00 UTC и по `backup-now`, хранятся последние 14, имя файла — таймштамп. **Внешняя выгрузка в S3-совместимое хранилище не реализована**, как и предусматривает сам текст ТЗ («если для S3 нужна зависимость — не добавляй, зафиксируй в HANDOFF»): без стороннего SDK пришлось бы реализовывать подписанные запросы AWS SigV4 с нуля — риск тонких ошибок в продакшене ради двух-трёх пилотных недель того не стоит. При заданных `BACKUP_S3_*` сервер лишь пишет в лог, что переменные заданы, но выгрузка не реализована — остаются только локальные копии на том же диске (см. §9.2 ТЗ — решение о внешних копиях зарезервировано за заказчиком) |
| Восстановление | `npm run admin -- restore --file …` — простое копирование файла (сервер должен быть остановлен, как требует ТЗ; скрипт не проверяет и не может проверить, что сервер остановлен — это ответственность оператора, о чём скрипт печатает явное предупреждение) |
| `/healthz`, `SIGTERM`, `Origin` | Health-check без сессии, проверяет `SELECT 1` через `store.ping()`. `SIGTERM` — `server.close()` дожидается текущих соединений, затем закрывает базу (`store.close()`) и выходит. Проверка `Origin === PUBLIC_URL` — только при `DEMO=0`, на всех изменяющих методах, включая вход/выход/приём приглашения |
| Лог запросов без персональных данных | Добавлен построчный лог `метод путь(с заменёнными ID) статус длительность userId` (`redactPath` в `server/index.js`) — раньше построчного лога запросов не было вообще. ID-сегменты вида `evt_…`/`usr_…` заменяются на `:id` по regex `^[a-z]+_[A-Za-z0-9_-]+$`; тела запросов/ответов, email, имена, телефоны и пароли никогда не попадают в лог ни этим механизмом, ни каким-либо другим в проекте |
| Демо-пользователям задан `email`/`status` | У демо-пользователей (`server/demo/seed.js`) не было полей `email`/`status`, которые требует новая модель сессий (`resolveSession` проверяет `status === 'active'`) — без этого демо-вход перестал бы работать. Добавлены вымышленные `*.demo.test` адреса и `status: 'active'`; поведение стенда не изменилось, только сессии стали идти через тот же код, что и в проде |
| Что не начиналось из §9 ТЗ (решает заказчик) | Тариф хостинга с постоянным диском; подключать ли S3 с первого дня; юрисдикция и требования к персональным данным пар; когда подключать реальную отправку писем (`server/mailer.js` — точка расширения, `sendInvite` пока ничего не отправляет); домен `PUBLIC_URL` боевого сервиса |

## Предтестовая доработка MVP (docs/specs/09-mvp-polish.md) — найденные причины и решения

| Пункт | Как сделано |
|---|---|
| **Критично: время задачи расходилось на экранах** | Два независимых бага, оба обходили часовой пояс пространства. (1) `web/js/ui/taskDialog.js` заполнял поля даты/времени формы редактирования через `new Date(task.dueAt).toISOString()` — это всегда UTC, а не пояс пространства; форма показывала «сырой» час UTC. (2) `web/js/views/taskList.js` брал часовой пояс для отображения списка из `listData.timeZone` — поля, которого сервер никогда не возвращает (это `project.timeZone`), поэтому срабатывал запасной вариант `Intl.DateTimeFormat().resolvedOptions().timeZone` — часовой пояс БРАУЗЕРА. Отсюда и наблюдение «02:52 GMT−7 в списке, 09:52 в форме»: список показывал время в поясе браузера тестировщика (Тихоокеанское время, отсюда и GMT−7), форма — в UTC, ни то ни другое — не пояс пространства. Исправлено: `taskDialog.js` теперь принимает `timeZone` и заполняет поля через `localDate`/`timeIn` (те же функции, что использует остальной интерфейс); `taskList.js` берёт `project.timeZone`. Дополнительно на сервере (`server/tasks.js`) сохранение `dueDate`+`dueTime` шло через `new Date(`${date}T${time}:00`).toISOString()` — без явного смещения эта строка парсится в часовом поясе **процесса сервера**, не пространства; добавлена `localDateTimeToMs(date, time, timeZone)` (`server/time.js`, тот же приём смещения через `Intl`, что уже был у `startOfLocalDay`) и весь путь записи срока переведён на неё. Заодно убран `timeZoneName: 'short'` из `dateTimeIn` (`web/js/format.js`) — раз пояс теперь везде совпадает и один на пространство, показывать «GMT+3» в каждой обычной подписи незачем (ТЗ, §3.1: «не выводи неуместный GMT−7 без необходимости»). Тесты: `test/time.test.js` (новый, включая пояс с переходом на летнее время), `test/tasks.test.js` (сохранение срока со временем в поясе пространства, не сервера) |
| Подписи стартового плана расходились с датой | `TASK_CHECKLIST` хранил статичный текст-подсказку («за 10 мес. до свадьбы»), а реальный срок при коротком сроке подготовки сжимается (`computeChecklistDueDates`) и может оказаться намного ближе, чем в статичной подписи — ровно случай из ТЗ (свадьба 26 января, подпись «10 мес.», дата — 12 октября). Подпись теперь считается функцией `describeSchedule` из уже назначенной даты, а не хранится заранее — не может разойтись с датой, которая показана тут же в панели. Если организатор вручную поправил предложенную дату, подпись меняется на «срок изменён вручную», а не продолжает показывать больше не относящееся к делу правило. Тесты в `test/checklist.test.js` |
| «Данные пары» считались незаполненными без родственника | `computeSetupSteps` (`server/events.js`) требовал не только оба имени партнёров, но и наличие дополнительного контакта с телефоном/email — противоречит ТЗ напрямую. Убрано: шаг «Данные пары» готов по именам. Аналогично шаг «Бюджет» засчитывался от любой строки сметы, в том числе появившейся автоматически при добавлении подрядчика-кандидата (сумма 0 в итоге) — теперь только от явного `budgetTarget`. Тесты обновлены в `test/wedding-setup.test.js` |
| Контакт по умолчанию получал роль «Родитель» | `editEventDialog.js` предзаполняло `<select>` роли значением `parent` для новых строк — организатор мог сохранить контакт, ни разу не взглянув на поле. Теперь новый контакт показывает неактивный плейсхолдер «Кем приходится» без предвыбора; роль сохранённого контакта по-прежнему подставляется при редактировании существующей записи |
| Первый шаг создания свадьбы был анкетой | Блок «Контакты, гости, бюджет — можно заполнить позже» убран из `createDialog.js` целиком (эти поля никогда не отправлялись как обязательные, но визуально удлиняли короткую форму и создавали ощущение анкеты). Заполняются позже в «Данные свадьбы» |
| «Данные свадьбы» — одна длинная форма | `editEventDialog.js` разбит на смысловые блоки внутри одного диалога — Основное / Пожелания пары / Бюджетный ориентир / Дополнительные контакты — с заголовками-разделителями (`.edit-section`). Отдельная страница не создавалась намеренно (правило 2 ТЗ: не плодить сущности; «Данные пары» как страница — по-прежнему предмет части II ТЗ 07, ещё не начатой) |
| Обзор: четыре пустые карточки перед подрядчиками | Причина — не отсутствие идеи по коллапсу, а то, что прежний коллапс срабатывал только при *полном* отсутствии открытых задач в принципе (§4.3 ТЗ 07). У «Тест UX + Аудит» (без даты, с планом из 13 задач без сроков) открытые задачи ЕСТЬ, просто ни одна не попадает ни в «Требует внимания», ни в «Дальше», ни в «В работе», ни в «Ждём ответа» — старое условие не срабатывало, и все четыре зоны показывали полноразмерные пустые карточки. Добавлен общий вариант «пустая зона — одна строка» (`compactZone` в `web/js/views/overview.js`, класс `.zone--compact`): применяется в каждой из четырёх зон независимо, когда в ней самой нечего показать, а не только в едином крайнем случае. Блок «Настройка свадьбы» тоже стал компактнее: готовые шаги — одной строкой упоминания («Готово: Дата свадьбы, План задач»), полноразмерная строка с кнопкой — только у того, что реально требует действия |
| «Дальше» без даты просто повторял текст | Вместо статичной фразы «…укажите дату свадьбы» без действия теперь настоящая кнопка «Указать дату», открывающая «Данные свадьбы» с фокусом на выборе даты — тот же приём, что уже использует блок настройки |
| Новый подрядчик из пустой личной базы «терялся» | `openVendorPickerPanel` создавал запись в личной базе (`onSaved`), но не отмечал её чекбоксом — организатор должен был найти её в списке и отметить второй раз. Теперь новая запись сразу отмечена; привязка к свадьбе всё равно происходит только по явному «Добавить N» |
| Кандидат в смете не объяснял «итог 0» | `server/budget.js`: строка сметы получила поле `vendorStatus` (`candidate`/`confirmed`/`null` для ручных строк) — сервер уже знал эту информацию через `sourceEventVendorId`, просто не отдавал её. Клиент (`web/js/views/budget.js`) показывает у такой строки «Не входит в итог до подтверждения подрядчика», а у «Итого» — одну из трёх разных подписей в зависимости от состояния (нет строк / есть кандидаты, но ничего не включено / есть включённые). Чекбокс «Учитывать в итоге» получил видимый текст вместо только `aria-label` |
| Список задач начинался с двух рядов фильтров | `web/js/views/taskList.js`: видимыми остались поиск и «Статус»; «Ответственный», «Требует внимания», «Без срока», «Проверить ответ» и «Сортировка» — под кнопкой «Фильтры» с счётчиком активных условий, раскрывается автоматически, если хоть один из скрытых фильтров уже задан через URL |
| Демо-фикстуры не проходили новую модель данных | Проверено по коду, не только по внешнему виду стенда: демо-свадьбы (`server/demo/seed.js`) создавались до ТЗ 07 и не имели `partner1Name`/`partner2Name`/`titleIsCustom`/`eventDatePrecision` — читались с безопасными умолчаниями (`withDefaults`), но из-за этого «Данные пары» на демо-проектах выглядели пустыми, хотя имена очевидны из названия. Это не общее правило «разбирать любое название по +» (в проде это было бы ненадёжно для реальных фамилий/событий с другим форматом), а точечное исправление для собственных фикстур, где раскладка «Имя + Имя» задана нами же и известна заранее |
| Не проверено в этом заходе | Полный визуальный проход по мобильной раскладке (375 px) для перечисленных ниже правок; орфографический разбор всей микрокопии; тексты пустых состояний за пределами перечисленных выше конкретных случаев — эти пункты не тождественны найденным причинным ошибкам и не были специально протестированы, только не тронуты, где уже работали корректно |
